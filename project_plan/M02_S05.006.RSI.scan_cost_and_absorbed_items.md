## 2. 第 1 项：缓存旁路是个被上游修复取代的占位符

`transcripts.go:359` 原本写的是 `case !ok || isAgentDatabase(candidate.File):`——即**每次扫描都强制重解析所有 agent DB**，绕过 size+mtime 缓存。理由本身正当：DB 的 mtime 不反映已提交的 WAL 写入。

但 git archaeology 给出了更准确的解释：

- 旁路引入于 `5b81005`（19:27:03）
- WAL 感知的 `agentEvidenceStat` 引入于 `43251ae`（19:27:24）

**相隔 21 秒。** 旁路是写 WAL 感知 stat 之前的占位符，真正的修复落地后没有人回来删掉它。`agentEvidenceStat`(agent_extra_transcripts.go:192) 返回 DB+WAL 的合并 size/mtime，已经能检测到纯 WAL 写入，旁路成了纯浪费。

**验证 WAL 检测确实有效时踩的坑（值得记）**：第一版验证用两次独立的 `sqlite3` 调用，结果「plain stat 和 WAL-aware stat 都检测到了变化」——看起来两者等价、旁路无意义。**这个结论是错的**：关闭 sqlite3 连接会 checkpoint 并截断 WAL，所以纯 WAL 写入这个场景根本没被构造出来。改用**持久连接**（stdin 管道 + SYNC 哨兵）重测，才测到真实情形：主 db 文件纹丝不动停在 4096 字节，而 db+wal 合计从 16488 涨到 24728。

`transcripts.go:793` 的延后守卫**保留**——它把二进制 SQLite 挡在 JSONL 尾读之外，删掉会让 state.db 走一次无意义的 256KB tail parse。

## 3. 第 2 项：wrapper 把多会话 API 塌缩成单条 trace

删掉的四个：`newExtraOutputUsageDecoder`、`parseExtraTrace`、`parseHermesStateDB`、`parseOpenCodeDBTrace`。后两个返回 `traces[0]`——一个装着多会话的 DB 在测试里永远只被看见第一条，**生产回归会被绿测试掩盖**。

测试改为直调注册表自己的解析路径（`parseExtraSessions` / `parseOneExtraSession` / `traceBySessionID`），`TestHermesAndOpenCodeSQLiteParsers` 改为每个 DB 播种**两个**会话并断言两个都回来。

**变异测试确认断言有效**：注入 `traces[:1]` 后测试如期失败（`expected both hermes sessions, got 1`），随后还原。

## 4. 第 3 项：Antigravity 只配 timeline 档

`antigravity-cli/brain/<session>/.system_generated/logs/transcript.jsonl`，作为 gemini 的第二证据根接入。

**实测决定了档位**：44783 条记录，**0 个 token/usage 字段**。每条都带 `created_at`，所以会话时间跨度是真的；但这个语料对 token 指标必须**零贡献**。按仓库规则「一个 vendor/signal 只能以它诚实支持的档位上线」，它只进 timeline。

两个实测细节：

- **语料是活的**：7 天内 23 个文件，当天 4 个——不是历史残留。
- **`transcript_full.jsonl` 与 `transcript.jsonl` 逐字节相同**。所以文件名用**精确匹配**而非前缀匹配：两个都收会让每个会话被计两次。

验证：102 文件 → 22087 事件 → **0 条 trace 声称 token**。

## 5. 第 4 项的计划偏差：头条计数器被自己人消灭了

计划里 RSI 面的头条是「`transcripts.go:359` 强制重解析计数器」，并且设计意图是「修完它应该归零，形成观测→发现→改进→验证的闭环」。

**但第 1 项在同一批次里就把那个浪费删掉了。** 现在再上这个计数器，它会是一个**结构性恒为零**的指标——正是「绝不虚构」要防的那类东西（一个永远显示 0 的仪表会被读成「已测量且为零」，而不是「无事可测」）。所以这一项被**放弃**，不是延后。

替代的是一个**已测未用**的发现：`transcriptEvidenceIndexStats`(evidence_index.go:16-28) 每次 reconcile 都在算 `Elapsed`/`VisitedEntries`/`PrunedDirectories`/`AgedOutFiles`，赋给 `index.lastStats`，随 `indexed.Stats` 一路抵达 `transcripts.go`——**然后全仓库零消费者**（grep 确认）。数据一直在算，只是被丢掉。

### 5.1 两个诚实性陷阱（都是实测踩出来的）

**陷阱一：`evidence_index.go` 的显式清零。** 非 reconcile 的 pass 会把 `VisitedEntries`/`PrunedDirectories`/`Elapsed` **显式清零**。直接呈现会把「本次没测」渲染成「耗时 0ms」。实测两次连续 pass：

```
pass1 reconciled=true  elapsed=1.173532166s visited=28145 pruned=934 agedOut=9060
pass2 reconciled=false elapsed=0s           visited=0     pruned=0   agedOut=9060
```

注意 `agedOut` 在两次都是 9060——它描述的是**索引当前内容**而非本次走查，所以它不需要守卫，另外三个需要。

**陷阱二（装机后才发现，是本 sprint 最重要的一条）：只报「本次 pass」等于几乎永远不报。** 第一版实现严格按陷阱一处理：非 reconcile 就什么都不出。装机实测发现 `walk_measured` 在**稳态下每一次都是 false**——索引大约每进程只 reconcile 一次，所以这个开销只在冷启动的那一瞬间可见，之后整个进程生命周期都是空白。

这在诚实性上无懈可击，在实用性上**和一个恒为零的计数器是同一类废物**——正是我在 §5 开头否掉头条计数器的那个理由。

修法：索引额外保留 `lastWalk`（最近一次**真的走了**的测量）与它的 `MeasuredAt`，`lastStats` 的清零语义**原样不动**（有测试锁着）。对外 `WalkMeasured` 表示「有过一次真实测量」，`WalkFresh` 表示「本次 pass 自己走了」。两者分开，读者既拿得到数，也知道这数是不是刚测的。

### 5.2 落地内容

- `TranscriptScanCost`(types.go)：`WalkMeasured`/`WalkFresh`/`MeasuredAt`/`ElapsedMs`/`VisitedEntries`/`PrunedDirectories`/`AgedOutFiles`。
- `transcriptScanCostFrom`(transcripts.go)：从 `LastWalk` 取走查数据，从 `Stats` 取 `AgedOutFiles`（后者描述索引内容）。
- 两个新 signal：`evidence_out_of_horizon`（范围外，不是缺口）与 `transcript_scan_expensive`（阈值 750ms，只有真测量过才比较）。
- 新 baseline `evidence_walk_cost`：未测量时值为 `no_data`、状态 `unavailable`，**绝不出 0ms**。
- UI：三语 6 个 signal 文案 + `evidenceWalk`/`pruned` 两个词条；扫描说明行追加走查开销，未测量则整段不出现。

**为什么 `deferred` 与 `aged_out` 必须分成两个 signal**：本机 3474 deferred 对 9100 aged-out。前者在范围内、本轮未扫（是缺口），后者在 7 天地平线之外（不是缺口）。`evidence_index.go:20-23` 的注释早就写明了这个区分，但它从未到达界面——合成一个数会把范围外的量算进覆盖缺口，读起来像故障。

## 7. 一次误判，记明

装机后 5 分钟内 `parsed_files` 一直是 0、`transcript scan wait cancelled`、累计 CPU 2 分钟，我**一度判定是自己引入了 hang**，并开始怀疑新加的 Antigravity 目录谓词放开了剪枝。

实测否掉了这个怀疑：gemini 根走查 72ms / 23 文件 / 剪枝 466；完整快照 34s 完成并给出正常数据。真实原因是**冷启动首扫本来就要几十秒**，而我在用短超时反复轮询——每次轮询都带着自己的 context，超时就取消，于是永远看不到那次扫描的结果。安静等一次就拿到了 78/78。

**教训**：冷启动期的 `parsed_files=0` 是既有文档写明的预热态（计划文件的 Verification 一节就写了「先打 `/api/refresh` 并等 `parsed_files>0` 再做任何 A/B」），我明明读过还是踩了，因为轮询本身制造了取消。**验证长操作时，超时要长于操作本身，否则你测的是自己的超时。**
