# M02_S05.005.PERF — 历史压缩（热明文 + 冷归档）

## 1. 用户诉求与约束

用户原话（两段，分别决定了范围与形态）：

> 我们是不是没有特地去对 history 做过压缩之类的操作？

> 我们在做这件事情的时候，还是要注意语义的完整，并且要避免由于迭代中的失误导致数据坏掉。所以，我们用的这种转换还是要可靠一点。

用户同时明确判断「如果一年只累积几十上百兆，那就完全无所谓」——**这句话是范围的上界**：本方案不是为了省磁盘，是为了在保留全部数据的前提下让存储停止失控。删除策略因此被排除。

「避免数据坏掉」直接决定了两个设计选择（§3、§4）：提交顺序与整月原子重写。

## 2. 实测基线（2026-09-19 / 2026-09-20 两次取样）

| 文件 | 大小 | 行数 | 读者 | 保留 | 压实 |
|---|---|---|---|---|---|
| `history.jsonl` | 53.2MB | 5221 | `loadLocalHistoryState`（history.go:82） | 30 天 | 有，仅启动时 |
| `lifecycle.jsonl` | 33.3MB | 40054 | **无任何读者** | **无** | **无** |
| `throughput.jsonl` | 23.0MB | 28259 | `loadThroughputHistoryStore`（throughput_history.go:83） | 30 天 | 有，仅启动时 |

**两条我自己先前的误判，必须记明：**

1. **history/throughput 并非无界增长**——它们有 30 天保留，109MB 更接近稳态。真正无界的只有 `lifecycle.jsonl`：唯一既无读者也无保留的存储。
2. **压实只在启动时发生**（history.go:132、throughput_history.go:157）。进程内长跑期间三个文件都单调增长。本机重启约 2.4 次/天（34 天 81 次 `startup`），所以「仅启动时」这个节奏可接受，但它决定了方案**不能依赖运行期压实**。

## 3. 形状：为什么是「热明文 + 按月 gzip 分区」

- **写路径完全不动是硬约束。** `appendHistorySampleFile`(history.go:298-325) 与 `lifecycleLog.record`(lifecycle.go:221) 对**每一行**做 `file.Sync()`，崩溃最多丢 1 行。块缓冲压缩会把这个保证降级到数百行量级。因此压缩只能发生在压实时的冷段，绝不能进入 append 路径。
- **月分区让 keep-forever 与有界读取同时成立。** 保留窗口 30 天，读者最多打开最近 2 个分区即覆盖全窗口；更早的分区永不再读、也永不删除。分区由**文件名**判定，无需打开旧文件。单一归档文件做不到这点——它会随年份线性变大并在每次启动被整读。
- **每个月分区整体原子重写，而不是往归档里追加 gzip 成员。** 追加成员看起来更划算（14 个成员 1.77MB vs 单成员 1.75MB，只差 1%，`Multistream(true)` 可透明读回），但**崩溃场景否掉了它**：一个被截断的半成员若留在归档中间，会让**它之后的所有成员都读不出来**（实测 `flate: corrupt input before offset 154`，100 行只读回 28 行）。追加方案必须额外实现「识别并丢弃不完整尾部成员」，那是自造机制。整月重写用的是仓库**已有**的 temp→`Chmod`→`Sync`→`Close`→`rename` 模式，没有截断态。
- 成本实测可接受：解压既有分区 + 合并新冷行 + 重压缩整月 = **212ms**（对比追加成员 136ms），仅在启动压实时发生。压缩级别选默认而非 level 9（后者多花近一倍时间只多换 9%）。

## 4. 可靠性：对应「避免数据坏掉」

四个失败模式实测全部为**可检测**行为，不存在无声丢失：

| 场景 | 实测结果 |
|---|---|
| 归档尾部截断 | 恢复 4408/4571 行，`scanner.Err()` = `unexpected EOF`（非 nil，可检测） |
| 归档中段位翻转 | 报错非 nil（CRC / token too long），不会静默当成正常数据 |
| 明文 vs gzip 混淆 | magic byte `1f 8b` 可判别，不依赖扩展名 |
| 半成员留在归档中段 | **污染其后所有成员**——这正是否掉追加方案的原因 |

**提交顺序是核心：先原子重写月分区，成功后才原子重写热文件。** 两步之间崩溃 → 数据在归档与热文件中**同时存在**，而非丢失。反过来会真丢数据。

去重由既有机制吸收：`appendRetainedHistorySample`(history.go) 按 `sample.At` 去重，`loadThroughputHistoryStore` 以 `minute.At` / `legacyThroughputKey(fact)` 作 map 键。`lifecycleEvent` **没有唯一键**，但它也没有读者——重复的后果仅是归档多一份副本，不影响任何指标。**不为它造唯一键或去重层**（那是给不存在的消费者做预防性抽象）。

**两个必须一起修的洞（对抗评审提出，已核实）：**

1. **`os.Rename` 原子但不持久。** 既有 `rewriteHistorySampleFile` 与 `rewriteThroughputHistoryFile` 都没有 fsync **目录**。断电可能丢掉归档的 rename 而保留热文件截断的 rename——那就是**静默丢失**，正是本方案要防的。新增 `syncDir(dir)`，在两次 rename 之间调用。
2. **分区读取出错必须中止整次压实。** 若读既有分区时 `scanner.Err() != nil`，绝不能拿残缺结果去重写分区（那会真丢历史），必须放弃本次压实并保持热文件原样。由 `TestUnreadableArchivePartitionFailsLoudlyAndKeepsHotFile` 锁定。

## 5. 复用既有机制，不新增抽象

- 跨进程锁复用 `internal/historyfile.Acquire(path)`——锁 `path+".lock"` 侧车文件，能跨越数据文件的原子 rename。**归档不得有自己的 `.lock`**，否则引入两把锁的加锁顺序问题（`TestHistoryOperationsShareCrossProcessLock` 守着这条）。
- 原子重写照搬 `rewriteHistorySampleFile` 的结构，含在任何错误分支删临时文件的 `cleanup` 闭包。
- 归档路径沿用三个存储已有的同目录兄弟文件惯例（`throughputHistoryPath` / `lifecycleLogPath` 都是 `filepath.Join(filepath.Dir(historyPath), ...)`）。
- 压缩用 `compress/gzip` 标准库。`internal/httpencoding.Gzip` 是 HTTP 响应用的一次性全量压缩，形状不匹配（无 level、无流式），不复用。

## 6. lifecycle 的额外一刀：省 20.8MB

按字段拆解 32.7MB，`snapshot_recorded` 行上的 `host_app_processes` + `runtime_processes` 占 **63.6%**。

**对抗评审称这些字段与 `history.jsonl` 的 `host_app_process_summary` 逐字节相同——我实测证伪了这个说法**：按 `at` 精确匹配 **0 命中**（lifecycle 的 `at` 是事件时刻，history 是快照时刻），按 ±5s 邻近匹配到 4620 行，**内容相同 0 行**。比例也不是评审说的 76.8%，是 68.4%。

但底下有一个**真实的冗余**：lifecycle 的副本是 history 的**严格子集**——同样的进程、同样的 `cpu_percent`/`memory_bytes`/`pid`，只是少了 `key`/`direct_sessions`/`subagent_sessions`/`unknown_role_sessions` 四个字段。

所以**只删 `snapshot_recorded` 上这两个字段**（`lifecycle.go:335` 一个 if）。`snapshot_aborted` 上的**必须保留**——快照失败时 history 里根本没有对应行，那是唯一证据，删掉就把「当时什么情况」变成不可知。由 `TestLifecycleKeepsProcessRostersOnlyWhereHistoryHasNone` 双向锁定。

## 7. 落地内容

新增 `history_archive.go`（258 行），三个存储共用：

| 函数 | 职责 |
|---|---|
| `archivePartitionPath(dataPath, month)` | `history.jsonl` → `history.2026-08.jsonl.gz` |
| `archivePartitionsSince(dataPath, cutoff)` | 按**文件名**筛出仍在保留窗口内的分区并排序 |
| `readArchivePartition/readArchiveLines` | 读回；缺文件 = 无行无错，读坏 = 返回错误 |
| `writeArchivePartition(path, lines)` | 读回既有 → **去重** → 整体重压缩 → 原子替换 → `syncDir` |
| `archiveColdRows(dataPath, rows)` | 冷行按月分组，逐月落盘 |
| `syncDir(dir)` | rename 的持久化补丁 |

改动点：
- `history.go`：`loadLocalHistoryState` 先读归档分区再读热文件；抽出 `consumeHistoryLine` / `hotSampleCount`；新增 `compactHistorySampleFile`；`rewriteHistorySampleFile` 末尾加 `syncDir`。
- `throughput_history.go`：同构（`consumeThroughputLine` / `hotRecordCount` / `compactThroughputHistoryFile`）。另补三处欠账：`appendThroughputHistoryRecords` 加 `file.Sync()`（**今天就没有逐行 fsync**）；`rewriteThroughputHistoryFile` 加 `Chmod(0o644)` 与 Close/Rename 失败分支的临时文件清理。
- `lifecycle.go`：新增 `(*lifecycleLog).compact(now)`（**纯按行处理，只用 `lifecycleLineTime` 解 `{at}`，绝不 `json.Unmarshal` 成 `lifecycleEvent`**——需要的是切分器，不是类型化读者）；`rewriteLifecycleLogFile`；`lifecycleEventFromSnapshot` 的字段裁剪。
- `tray.go`：建 `lifecycleLog` 后调一次 `compact`，与另两个 load 相邻。

**明确不做**（各有实测理由）：
- **不缩短 JSON key**：gzip 字典已消除重复键名，实测原始 51.8→26.8MB(-48%) 但压缩后仅 -12.5%；且这些 tag 与 live API 共用，改名直接破坏 UI。
- **不截断浮点**：仅省 8.4%，丢失真实测量精度，`evidence_model_test.go:978` 还锁着 `AttentionSharePct`。
- **不加删除策略**：压缩后一年约 30MB 归档，收益不足以换取数据损失风险。

## 8. 一个真 bug：重复归档（测试抓出）

`TestArchivePartitionsSpanMonthsAndMergeOnSecondCompaction` 第一次跑出 **7 行而非 4 行**，三个日期各重复一次。

根因：`compactHistorySampleFile` 收到的 `samples` 是**归档+热文件合并后**的集合，所以**已归档的行每次压实都会被再归档一遍**。分区会在每次重启时无界增长，而且**因为 gzip 藏起了字节，从磁盘大小上看不出来**。

修复：`writeArchivePartition` 读回既有内容建 `seen` 集合，逐行过滤，无新行时直接返回。这也正是「整月重写幂等」这个性质的落实点。

**这个 bug 只有归档往返测试能抓到**——既有夹具把过期行放在 -40 天（超出 30 天保留 → 直接丢弃，从不归档）、保留行放在 2 天热窗口内，**冷集恒为空，归档路径零覆盖**。所以「预期会红的测试没红」当时是**覆盖缺口的信号**，不是好消息。

**五门全绿**：`go vet ./...`；`go test ./...`（`ok agentload 7.846s`）；`npm --prefix ui run build`；`node scripts/validate_locales.js`；`./build_macos_app.sh`。

**真实数据迁移**（备份 `/tmp/agentload_backup_pre_install_20260920_103529`，73534 行 / 109.5MB）：

| 文件 | 迁移前 | 热文件 | 归档 | 合计 | 行数守恒 |
|---|---|---|---|---|---|
| history | 5221 行 / 53.2MB | 514 | 4199 | 4713 | -508 = 保留窗口过期数（Python 独立复算 **508**，精确吻合） |

**总计 109.5MB → 12.26MB（-88.8%），零行丢失。**

**归档内容校验**：三个存储共 65425 行归档，`invalid_json=0`，落在热窗口内的行 `0`，最新归档时间戳均为 2026-09-18（恰好 2 天前）。

**幂等性（重启复核）**：重启后二次压实，history 与 throughput 的归档**字节完全相同**（1671157 / 1119643）；lifecycle 增 6 行，经核验是 2026-09-18 10:35–10:40 恰好跨过 2 天边界的 heartbeat，属正确行为而非重复归档。

**权限**：3 个热文件 + 6 个归档分区全部 `0644`（迁移前 `throughput.jsonl` 是 `0600`，`Chmod` 补丁生效）。

**语义完整性**（对应用户「注意语义的完整」）：`/api/snapshot` 的 `trends.windows` 五个区间全部正常渲染，最长区间跨至 **2026-08-21**——整整 30 天，**只可能来自归档**。`history_complete=false` 仅出现在 15D/30D，是既有的 7 天 transcript 证据地平线所致（`metrics.go:239`），与本改动无关。

**运行时**：装机后 `/api/refresh` → `parsed_files=80`（非冷启动 0），空闲 CPU **0.3%**（门禁 <1%），RSS 387MB。
