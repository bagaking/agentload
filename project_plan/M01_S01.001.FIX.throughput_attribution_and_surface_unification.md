# M01_S01.003.FIX — 吞吐归属诚实性与 popover 面性统一

## 1. 背景与问题

用户在使用中连续报出六个问题，其中三个是真 bug，三个是品位问题。逐条记录根因，防止再犯。

### 1.1 tps 整体变空（真 bug，本轮最重要的一条）

**症状**：吞吐读数显示 `--/s`，副标题「近期 transcript 文件过多，无法保证完整采样」。

**用户原话**：

> 「tps 不显示了，有 "近期transcript文件过多,无法保证完整采样" 的提醒，这是不是不对，我觉得可以接受降低频率，而不能接受没有值 / 而且 transcript 多，正是最需要分析 tps 的时候」

**根因**：本机近 15 分钟内有 120 个活跃 transcript，而 `liveTokenRateMaxFiles` 写死 96。超限时 `syncEvidenceFilesLocked` 调用 `markLimitedLocked(now, file_capacity)`，`liveTokenRateSampleFromFacts` 随即把整个 sample 判成 `unavailable` 并丢弃数值。

**这个设计错在两层**：

1. **语义错**：采到的那 96 个文件里的 token 都是真实观测到的。正确语义是「下限值（floor）」，不是「未知」。把「不完整」等同于「不可知」，是对诚实未知原则的误用——诚实要求不假装完整，不要求什么都不给。
2. **选择错**：超限时 `break` 丢弃后来的候选。索引按 mtime 倒序，所以丢掉的恰恰可能是最热的文件。

**修复**：

- `liveTokenRateMaxFiles` 96 → 256。
- 超限时改为 `evictColdestFileLocked`——淘汰 mtime 最旧的已跟踪文件给更热的候选让位；若候选本身比所有已跟踪文件都冷，则保留现状（此时上限已经握着最热的子集）。
- 新增 `coverage: "partial"` 语义：数值照常出，附 `tracked_file_count` / `eligible_file_count`，UI 前缀 `≥` 并写明「下限值：已采样 96/120 个近期 transcript」。
- 删除 `liveTokenRateUnavailableFileCapacity` 常量及其 en/zh/ja 文案（不留兼容层，遵循 AGENTS.md）。

**测试**：`TestLiveTokenRateSampleFromFacts` 扩展——partial 事实必须保留数值、state 仍为 `live`、coverage 字段齐全。

### 1.2 空白面板（真 bug）

**症状**：切到吞吐页，整页全空，连「暂无数据」都没有。

**根因**：`TrendSuite` compact 模式只渲染当前 lane，但空状态判断用的是 `laneSummaries.length`——即「任意 lane 有数据」。当吞吐还在冷启动预热、活动 lane 已有数据时，条件为真 → 渲染出 `trend-compact-view` 容器，但里面的 `currentLane === "throughput" && throughputSummary` 为假 → 空容器。

**修复**：新增 `laneHasData`，compact 模式下只看当前 lane 的 summary。

### 1.3 未归属占比过高（真 bug）

**根因**：`liveTokenRateSampler` 按 `tool\x00transcript路径` 记账，而 `LiveTokenProjects` 映射表只覆盖「能映射到活进程」的 session。映射不上的 transcript 直接落入 `unassigned`——但它的路径本身就编码了项目名。

**修复**：`liveTokenRateProjectFromSessionKey` 从 session key 反解项目，先试 `extractClaudeProjectFromPath`（Claude 的编码项目目录）；其余路径必须先由 `resolveRepoBoundary` 证明它确实落在一个真实仓库里，才取目录名，否则返回空。

**关键的克制**：这不是万能兜底。transcript 仓库（codex 的 `~/.codex/sessions/2026/09/14/`）不是 checkout，不含任何项目信息 → 诚实记为 unassigned。第一版只靠 `pathProjectName` 的通用名黑名单挡这种路径，被对抗式复审打穿（叶子名 `"14"` 不在黑名单里，见 §4 #2）——黑名单挡的是「名字看起来很通用」，而真正该问的是「这个路径到底在不在仓库里」。测试 `TestLiveTokenRateProjectsForBucketsRecoverUnmappedSessions` 用真实 codex 日期树锁住三个方向：能反解、不该反解、真在仓库里就该认出来。

### 1.4 品位问题三条

- **周期选择重复**：并发页 head 与 footer 各画一份。compact 模式下 head 那份删除。
- **周期选择现代化**（用户要求「放在正中间、mac 导航栏 hover 魔法效果、改成面性」）：`TrendRangeRail` 抽为独立文件（`TrendSuite` 是懒加载的，footer 拿不到那个 chunk）；居中悬浮于 tab 栏上方；单块高亮底板在选项间滑动（`:has()` + `transform`），hover 跟随光标、移开回落选中项。
- **面性设计全面铺开**：diagnostics(9)、online-processes(8)、system-resource-inspector(7)、activity-process-trend(5)、system-process(2)、lineage(1) 的发丝线边框改为色块托盘。`lineage.css` 的树形缩进竖线保留——那是结构语义不是装饰。

## 3. 指标语义变更（须同步 docs）

`LiveTokenRateSample` 新增三个字段：

| 字段 | 含义 | 缺省行为 |
|---|---|---|
| `coverage` | 仅当值为下限而非完整测量时设为 `"partial"` | 省略 = 完整测量 |
| `tracked_file_count` | 实际采样的 transcript 数 | 仅 partial 时出现 |
| `eligible_file_count` | 符合条件的 transcript 总数 | 仅 partial 时出现 |

**这是对诚实未知原则的一次细化，值得单独记住**：原则的完整表述应该是「不可测的渲染为显式的未知状态；**部分可测的渲染为带覆盖度标注的下限值**」——而不是「凡不完整即未知」。后者会在数据最密集、用户最需要的时刻把指标关掉。

## 5. 性能优化（profile 驱动，2026-09-14）

用户问「优化了吗」——上一轮把 `resolveRepoBoundary` 的 stat 风暴留作性能项，这轮补上。**先量后改**：新增 `snapshot_benchmark_test.go`（需 `AGENTLOAD_BENCH_REAL=1`，默认跳过，因为它读开发者本机 home）。

**实测基线**：一次 warm refresh 116ms / 16MB / 26k allocs。pprof 显示 **63% CPU 是裸 syscall，其中 `resolveRepoBoundary` 独占 53.84%**（23.72s / 44.06s，占全部 `os.Stat` 的 100%）。

根因比预想的严重：`setTraceProjectPath` 是**按 transcript 的每一行 cwd 调用**的（transcripts.go:1200/1251/1315/1387），且每次走两遍目录树。同一个 cwd 每轮 refresh 被重复解析上万次。

| 改动 | 结果 |
| --- | --- |
| `resolveRepoBoundary` 加 30s TTL memo（独立 mutex，慢走在锁外，超 4096 条整体清空） | 隔离基准 **19096 ns → 154 ns，快 124 倍**；pprof 中 `os.Stat` 从 53.84% → **0.19%**。TTL 是诚实性保障：用户中途 `git init` 在 30s 内被看到，negative 结果同样过期，不会把 unassigned 钉死。由 `TestResolveRepoBoundaryMemoExpiresSoNewReposAreSeen` 锁定 |
| ~~lsof 结果按 PID 集合缓存~~ | **已回退**。隔离测试确实 54ms → 3µs（还顺带发现 PID 列表来自 map 遍历、顺序随机导致 key 永不命中，需排序），但对抗式复审指出真实 refresh 间隔是 **5 分钟**（`process_refresh_target_seconds: 300`），popover 读的是缓存快照——52ms / 300s = 0.017% CPU。**我优化的是自己的压测循环，不是产品。** 删掉 |

**被实测证伪的建议**：复审提出「分类阶段每次扫描都重读每个前台 transcript 的 256KB 尾部」。加计数钩子实测：**3 次 warm refresh 共 0 次尾读**——`foregroundCutoff` 的 mtime 判断已经短路，成本模型假设了一个不成立的前提。

**过程事故（值得记）**：清理临时探针时用 `git checkout transcripts.go` 回退整个文件，**抹掉了本 session 未提交的 4 处修改**（`transcriptScanErrorIsGlobal`、worktree 归属、`--worktrees-` 前缀剥离、单文件解析错误不再置 `CoverageIncomplete`）。全部由测试立刻抓出并逐条还原。教训见 OPINIONS D-009。

## 6. 未归属成分核查（用户提问触发，2026-09-14）

用户问「未归属的都是些什么」。查实机而非猜：

**吞吐侧（`/api/live-token-rate`）：0 个未归属。** 15 个会话全部落到 6 个真实项目，coverage 为完整测量。§4 #2 的修复没有把归属能力改坏。

**快照侧（`/api/snapshot`）：未归属确实存在，但全部合理。** 按 `project_attribution_reasons` 分组后只有两类：
1. `missing_transcript=True` + `mapping_method=command_hint` / `fallback_session_id` —— AgentMux / Orca / ChatGPT 里刚起的 claude / codex 进程，**transcript 还没写出来**，因此不存在任何 cwd 证据。这正是 [[D-008]] 要求的行为：没有证据就不要编。
2. codex 的配置根锚在 home 下，`pathProjectName` 拒绝，同样诚实记为 unassigned。

数量随预热变化（冷启动 37/47 → 预热后大幅下降），因为 transcript 一旦落盘就能反解出项目。

**顺带查出一个真 bug（隐私脱敏器把说明文案吃掉）**：用户看到的归属理由是 `"no parsed transcript cwdlocal-path"`。根因在 `sanitizeEmbeddedAbsolutePaths`（server.go:908）——它从任意 `/` 开始截取候选路径，而 `cwd/project` 里的 `/project` 恰好通过 `filepath.IsAbs`，于是被整段替换成 `local-path`，连分隔符带后面的词一起吃掉。`and/or` → `andlocal-path` 同理。

修法：`/` 只有位于 token 边界（前面是空白或 `"'([{:=,`）时才可能是嵌入路径的开头。真实路径的脱敏完全不受影响，已由测试同时锁住两个方向：

| 输入 | 修复后 |
| --- | --- |
| `no parsed transcript cwd/project evidence` | 原样保留 |
| `and/or` | 原样保留 |
| `see /Users/me/secret/deep/file.jsonl now` | `see file.jsonl now`（仍然脱敏） |
| `path=/Users/me/secret/deep/file.jsonl` | `path=file.jsonl`（仍然脱敏） |

测试：`TestSanitizeTextForClientKeepsProseSlashesWhileRedactingPaths`。

**`topic--launcher--<uuid>` 不是 bug**：这些是 `~/.agentmux/scratch/topic--launcher--<uuid>` 真实存在的工作目录，名字难看但诚实。

## 7. 两条实机分歧的根因（用户截图与质疑触发，2026-09-14）

用户先看截图质疑「项目吞吐里未归属 368 token/秒、占 80%，这不太合理」——因为同一时刻的实时读数是 0 未归属；随后又指出「A 和 S 的数量不太对，光 agent mux 里打开的都不止这些了」。两条都是真 bug，根因互不相干。

### 7.1 同一份 token，两条归属路径写出两种桶

`publishLocked`（实时样本）走 `liveTokenRateProjectsForBuckets(...)`，带路径反解；`minuteFactLocked`（落盘分钟事实）却把**原始的** `sampler.sessionProjects` 直接传下去。于是任何「没有映射到进程」的 session 在 `metric_semantics.go` 里查不到项目名，**只在历史里**掉进 unassigned。同一批 token，取决于哪条路径写的，进了两个不同的桶——这正是实时显示 0%、趋势图显示 80% 的原因。

修复：`minuteFactLocked` 改用与实时样本相同的恢复函数。由 `TestLiveTokenRateMinuteFactsAttributeLikeTheLiveSample` 锁定（该测试最初失败于测试自身——空 `Config{}` 没有 usage root，`Configured` 为 false，样本在 `OutputTokensPerSecond == nil` 处提前返回，根本走不到项目循环；给测试补上 root 后才真正验证到归属）。

实机切换前后（`throughput.jsonl`，同一台机器连续分钟）：

| 分钟 | 未归属占比 | coverage |
| --- | --- | --- |
| 04:58Z | 35.2% | 无（下限被洗成精确值，见 §4 #1） |
| 05:00Z | **0.0%** | `partial` |
| 05:01Z | **0.0%** | `partial` |

### 7.2 子代理 transcript 借用父会话 ID，十个会话塌成一个

Claude 给每条 sidechain 行打上的 `sessionId` 是**父会话的 ID**（实测 `subagents/agent-*.jsonl` 与 `subagents/workflows/*/agent-*.jsonl` 首行均为 `isSidechain: true` + 父 ID）。而 `processClaudeTraceLine` 无条件采纳 `sessionId`，会话又以 `tool\x00sessionID` 为键——于是 AgentMux 那个开着十个子代理的会话，**十份 transcript 全部塌进父会话那一行**。

用户的直觉是对的，而且指对了地方：实机 15 分钟内有 37 份 claude transcript 被写入，界面只认出 21 个会话。

修复：sidechain 行借来的 ID 记为 `ParentThreadID`（父链接），不再覆盖本线程身份——文件名才是这条线程唯一的身份。新增 `jsonTrueField`（字节扫描，与既有 `jsonStringField` 同风格，缺键与 `false` 同义）。

**发现过程值得记**：第一反应是怀疑目录发现漏扫了 `subagents/`，实测 `claudeTranscriptDiscovery` 完整下降、只剪 `memory` 与 `tool-results`，发现阶段一份不少。**丢失发生在解析阶段，不在扫描阶段**——是解析把不同身份合并了。

修复前后（同机、重装后即刻）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| claude 会话数 | 21 | **37** |
| agentmux 行数 | 1 | **15** |
| 角色分布 | main 12 / unknown 9 | main 11 / **subagent 17** / unknown 9 |

两条回归测试对称锁定：`TestParseClaudeTraceKeepsSubagentIdentityWhenSidechainBorrowsParentSessionID`（子代理保住自己的身份、借来的 ID 变成父链接、角色判定为 subagent）与 `TestParseClaudeTraceStillAdoptsSessionIDOnMainTranscripts`（主 transcript 无 `isSidechain` 标记，必须照常采纳自己的 sessionId——防止守卫过度触发把真会话 ID 全剥掉）。

### 7.3 遗留的数据债：已落盘的错误归属无法回算

`throughput.jsonl`（20.8 MB、24268 条有项目的分钟）中，05:00Z 之前的分钟全部带着 §7.1 的错误归属：近 24 小时 69.4% 未归属、全历史 48.4%。修复只作用于此后写入的分钟，**任何回看超过修复时刻的窗口，未归属仍然虚高**。分钟事实里只有单向的 session hash，没有原始 session key，因此**无法重算**。待用户决策：丢弃历史重新开始，或保留并在 UI 上标注断点。
