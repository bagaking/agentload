# M02_S05 · Vendor 实机落地：grok 满证据，cursor/gemini 诚实分级

## 0. 为什么范围不是「三个都接」

用户要求接 gemini / cursor / grok 三家。落地前对三家做了实机取证，结论是**三家的证据水平不在一个量级**，按同一档位发布会直接违反北极星不变式（绝不虚构）。取证结果见 §1，范围裁决见 §2。

这不是缩范围，是 PLAN.md §7 已记录的否决理由在实机上第二次成立：

> vendor wave 2 里程碑化（Cursor/Copilot/Aider/Amp/Goose 齐上）｜广度当 checkbox 是品类致命模式（ccusage 赶工 codex 支持产出 91x token 虚报 #950/#1434）

## 1. 实机取证结论（2026-09-15，本机）

| 维度 | grok | cursor (CLI) | cursor (IDE) | gemini (agy/Antigravity) |
|---|---|---|---|---|
| 存储形态 | JSONL | JSONL | 单一全局 SQLite | 每会话 SQLite，正文 protobuf blob |
| 逐行时间戳 | **171/171、363/363、466/466 = 100%** | **0/33 文件含时间戳** | 有（composer 为 epoch ms，bubble 为 ISO 串） | 仅在 protobuf blob 内 |
| token 用量 | **逐轮 input/output/cached/reasoning** | **无** | `tokenCount` 字段存在但 13990 条全为 0；`usageData` 92 个全为 `{}` | **schema 无任何 token 字段**，90 库全扫无系统记录 |
| 成本 | **`costUsdTicks`（USD×10⁸）** | 无 | 无 | 无 |
| 会话 ID | UUIDv7，目录名 + argv `--resume` | UUID，目录名+文件名 | `composerId`（db key/列） | UUIDv4（db 文件名） |
| cwd 归属 | 三重冗余（目录名编码 / active_sessions / summary.json） | 目录名路径编码 | workspace hash + workspace.json | 仅 7/90 有 `workspace_uris` |
| 活跃映射 | **`active_sessions.json` 直给 `{session_id, pid, cwd, opened_at}`** | 无 | 无（进程表区分不出 IDE 空开 vs agent 在跑） | 无 |

三条决定性事实：

1. **cursor CLI transcript 每行只有 `role` 和 `message` 两个键。** 全量 33 个文件中含 `timestamp|createdAt|tokenCount|usage` 的文件数 = **0**。
2. **gemini 正文是 protobuf blob**（`typeof(step_payload)=blob` 实测），`steps` 表 schema 无 token 字段；经典 JSONL 路径全机仅剩 1 个文件。
3. **grok 的 `turn_completed.usage` 是逐轮增量，不是累计。** 实测 122 条 usage 行 output 序列非单调（`917563→282982→146484…`），且 `numTurns` 逐行不同。**若误判为累计（codex 那套），吞吐会被严重放大**——这正是 #950 的同一失效模式。

### 1.1 与现有管线的硬约束

`nonEmptyTrace`（transcripts.go:1801）在 `EventTimes` 为空时返回 nil。**没有逐行时间戳的 transcript 根本产不出 trace**。因此 cursor CLI 与 gemini 不是「多写点解析代码」的问题，是证据本身不支持 transcript 档位。

## 2. 范围裁决

- **grok → 满证据 adapter**：Process + Discovery + Transcript + Usage 四槽全填。
- **cursor / gemini → 维持诚实空壳**：capability 槽保持 nil。registry 注释（agent_registry.go:45-52）已把这条写成不变式——「Capability slots stay nil until their behavior has moved here; this prevents an agent name from implying evidence support」。`cursor` 现在的 `{ID: "cursor"}` 空壳是**刻意的**，本 sprint 不动它。

用户已在本轮明确选择此范围（选项「只做 grok 满证据」）。

## 3. OKR

- **Objective**：用证据最全的 vendor 验证 adapter 抽象可复制，同时把「证据不足就不发」从原则变成本轮的实际动作。
- KR1：grok 在 transcript / 会话身份 / 逐轮用量三个维度达到与 claude/codex 的证据对等。
- KR2：grok 的**逐轮增量**语义由测试锁定——蓄意改成累计的夹具必须让测试失败。
- KR3：cursor / gemini 的档位不因本轮"支持了三家"的表述而虚涨；矩阵/文档如实标注。
- KR4：argv 密钥脱敏对 grok 的 `-- <prompt>` 形态由回归测试守住。

## 5. 验收标准（量化）

1. grok 会话在 popover / dashboard 出现，带正确项目归属与逐轮吞吐；数值与 `updates.jsonl` 实测可对账。
2. 把 grok 夹具的 usage 改成累计语义 → 测试失败（语义锁有效性证明）。
3. `grok ... -- <含密钥 prompt>` 经 `sanitizeCommandForClient` 后密钥不出现在任何快照字段（测试断言）。
4. cursor / gemini 的 capability 槽仍为 nil；无任何 UI 位置为其渲染 token 或吞吐。
5. 四大门全绿（`go vet` / `go test` / `npm run build` 且 dist 与 src 一致 / `validate_locales.js` / `build_macos_app.sh`）。

## 7. 对 M02_S04 的修订要求

M02_S04（gemini adapter 与 conformance kit）成文于 2026-07-26，其隐含前提是 gemini-cli 的 JSONL transcript。实测推翻该前提：

- 本机实际在用的是 Antigravity CLI（`agy`），90 个会话为**每会话 SQLite + protobuf blob**，经典 JSONL 仅剩 1 文件。
- `steps` 表**无 token 字段**——M02_S04 的 KR1「证据对等」在 token 维度不可达，只能诚实标 unavailable。
- 接入成本远高于「≤1 周/vendor」基准（需引入 protobuf 解码，与仓库现行纯字节扫描的做法是两套世界）。

因此 M02_S04 的验收标准须重写为：以 grok（本 sprint）作为 conformance kit 的第二个样本，gemini 的接入降级为「进程存在性 + 诚实 unavailable」，protobuf 解码另立 spike 评估。
