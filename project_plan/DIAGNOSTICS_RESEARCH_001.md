# 诊断页调研：从“指标堆”到“证据控制室”

日期：2026-09-22

这轮调研基于当前诊断页代码、`/api/snapshot` 的真实本地快照、指标语义文档，以及仓库里已经吸收的可观测性参照。完整研究卡片和证据链保存在本地 researcher topic：
`.bagakit/researcher/topics/product/process-evidence-ia/`。

## 结论

诊断页最需要补的不是更多采集器，而是阅读顺序。页面应让人连续回答三个问题：

1. **现在发生了什么？** 近期活动、已知会话、可见进程压力、证据覆盖分别是多少。
2. **哪里有不必要的损耗？** 把归因损耗、覆盖延迟、扫描开销、token 可见性分开，并说明范围、时间、来源和下一步检查。
3. **可以怎样优化？** 每个建议都要有基线、假设、可逆实验、预期证据变化、验证条件和停止条件。

## 当前快照暴露出的可解释损耗

| 现象 | 当前值 | 应怎样解释 |
| --- | ---: | --- |
| 进程无法归因到会话 | 23 / 118 PID | 运行时压力可见，但不能算作已确认会话 |
| 会话证据信心不足 | 9 个会话 | 映射、时间或归因证据较弱 |
| 前景扫描延期 | 2,425 个文件 | 在配置范围内但本轮延期，属于覆盖延迟 |
| token 可见性 | 88 / 99 个会话 | 只有存在本地 usage 字段时才计为 measured |
| 最近一次证据走查 | 4,585 ms | 上一次完整走查的采集开销，不代表 Agent Load 消耗了全部机器资源 |
| 超出历史范围 | 10,459 个文件 | 明确不在历史地平线内，不应当显示成故障 |

这些数字不能相加，也不能压成一个“浪费率”。全机 CPU、内存、磁盘和网络是独立的系统压力事实，除非有可靠的进程级归因，否则不能称为项目损耗。

## 推荐的信息布局

### P0：只读损耗台账

用现有 `baselines` 和 `evidence_gaps` 生成统一行模型。每行包含：证据族、范围、测量时间/新鲜度、当前值、状态、影响维度、来源和“下一步检查”。延期扫描与超出历史范围必须是两行。

### P1：情况地图

把第一屏改成一张小型情况地图，明确区分 recent movement、known sessions、process pressure、mapping coverage 和 token coverage。每个数字都能进入对应的会话/进程证据。

### P1：优化实验队列

把现有 evolution insight 变成实验行，直接关联损耗台账或信号。没有实测收益时显示为 hypothesis，不自动宣称某种 Agent 配置更好。

### P2：证据血缘和时间线

支持从聚合数字进入采样时刻、贡献会话/PID、匹配方式、置信度和缺失原因，再补充只含元数据的事件时间线。暂不引入原始 prompt、默认回放或新的特权采集。

## 验收方式

用 warm、cold/incomplete、sparse/no-data 和高压力四类快照验证；三语渲染；检查每一行都有来源和状态；检查缺失、延期、超范围、measured zero 不互相混淆；检查每个实验都能回到可见证据行。
