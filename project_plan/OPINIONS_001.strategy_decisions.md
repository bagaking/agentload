## D-007 诚实未知不等于「不完整就不给值」

- **来源**：用户洞见（2026-09-14）。原话：「我觉得可以接受降低频率，而不能接受没有值 / 而且 transcript 多，正是最需要分析 tps 的时候」。
- **语境版本**：mini-sprint `M01_S01.001.FIX`（2026-09-14）。
- **内容**：吞吐采样器原先在活跃 transcript 数超出文件上限（96）时，把整个 tps 指标判为 `unavailable`（理由 `file_capacity`）。本机实际有 120 个活跃 transcript，于是指标长期为空。这是把「诚实未知」原则用错了方向：**已采到的那 96 个文件里的 token 全部是真实观测值**，正确语义是「下限值（floor）」，不是「未知」。修复后引入 `coverage: "partial"` + `tracked_file_count` / `eligible_file_count`，数值照出、UI 以 `≥` 标注覆盖度；并把超限策略从「拒收新候选」改为「淘汰最冷的已跟踪文件」——原策略按索引顺序 `break`，而索引是 mtime 倒序，丢掉的恰恰可能是最热的文件。
- **原理**：诚实未知的约束是**不许假装完整**，不是**不许给值**。两者混淆会产生一个特别恶劣的失效模式——负载越高、数据越密集、用户越需要看的时候，指标越是关掉。任何「不完整 → 整体不可用」的判定，都要先问一句：手上这份不完整的数据，本身是不是一个有意义的下限？如果是，就该带着覆盖度标注出货。
- **推广检查点**：凡是存在采样上限、截断、超时降级的指标，都要按这条复查一遍，不要只修 tps 这一处。**而且不能只查后端**——第三处发作证明前端的渲染门控会犯同样的错：把「某个附属数据没准备好」升级成「整块 UI 不渲染」，于是把同一块区域里已经可用的真实值一起连坐。审查 UI 时要单独问一句：这个 `? :` 的假分支，会不会把一个本来有值的东西也藏了？当天即照此复查出第二、第三处同类误用：(2) 文件事件监听出现 gap 时（`watch_incomplete`）同样把整个指标清空 5 分钟；(3) **前端** `TrendSuite` 把「有无趋势窗口」当作整条 lane 的存活条件，冷启动趋势未攒够时整条 lane 被过滤，连带把旁边**已经可用的实时吞吐值**一起藏掉。
- **对偶的失效模式见 [[D-008]]（有真值却藏起来 vs 没真值却编一个）。但有一个必要的例外，值得一并记住**：降级覆盖下**测得为零**时必须仍然失败关闭。理由是零下限在逻辑上恒真、毫无信息量，而读者会把它读成「什么都没发生」，真相却是「可能全都漏了」——这时诚实未知才是对的。所以完整规则是：**有正值 → 带覆盖度标注的下限；零值 + 覆盖降级 → 诚实不可用**。此例外由 `TestLiveTokenRateWatchGapFailsClosedAndForcesRecovery` 锁住（该测试在我最初的过度修正中失败，是它逼出了这条边界）。

## D-008 诚实未知的对偶失效：宁可 unassigned，不要自信的错桶

- **来源**：对抗式复审（opus 子代理）在 `M01_S01.001.FIX` 的改动上发现，由该轮改动自己引入。
- **语境版本**：mini-sprint `M01_S01.001.FIX`（2026-09-14），复审结论 §4 #2。
- **内容**：为了降低 unassigned 占比，`liveTokenRateProjectFromSessionKey` 在 Claude 编码目录之外回落到「取 transcript 所在目录名」。对 codex 的真实布局 `~/.codex/sessions/2026/09/14/rollout-<uuid>.jsonl`，这会取到叶子名 `"14"`——日期数字躲过了 `pathProjectName` 的全部通用名拒绝检查，于是**当天所有无关 session 被合并进一个根本不存在的项目「14」**。修复：非 Claude 路径必须先由 `resolveRepoBoundary` 证明自己落在真实仓库内，否则返回空。
- **原理**：这是 [[D-007]] 的对偶。D-007 讲的是「有真值却藏起来」，这条讲的是「没有真值却编一个」。两者都源于同一个偷懒动作——用一个看起来合理的代理值去填补不确定性。**代价却不对称**：藏掉一个真值，用户看到空白，知道自己不知道；编造一个错桶，用户看到一个具体项目名，会当真——而且错误会污染聚合，把不相关的数据合并在一起，比缺失更难发现。所以 unassigned 不是失败，是正确答案。
- **更锋利的一条教训在测试上**：这个 bug 有测试覆盖，却没被挡住。原测试用的是 `sessions/def.jsonl`，命中通用名黑名单所以通过；真实布局多了三层日期目录就穿透了。**测试用的是我脑内简化的路径，不是产品里真实存在的路径**——凡是断言「某种输入应当被拒绝」的测试，输入必须取自真实世界的样本，否则测的是自己的假设。
- **推广检查点**：所有「从路径/名称反解语义」的代码都要问：拒绝逻辑是基于**黑名单**（名字看起来不对）还是基于**证据**（能证明它是什么）？黑名单必然漏，因为世界能造出的名字比黑名单长。

## D-009 先量后改；以及「未提交的工作等于没有工作」

- **来源**：本轮性能优化的实测与一次真实事故。
- **语境版本**：mini-sprint `M01_S01.001.FIX` §6（2026-09-14）。
- **内容（先量后改）**：本轮两个优化，只有一个真的有用。`resolveRepoBoundary` 的 memo 在隔离基准上快 124 倍（19096ns → 154ns），pprof 里 `os.Stat` 从 53.84% 降到 0.19%；而 lsof 缓存在压测循环里 54ms → 3µs，看起来同样漂亮，**但真实 refresh 间隔是 5 分钟**，折算 0.017% CPU——它优化的是我的压测循环，不是产品，已删除。另有一条「每次扫描重读 256KB 尾部」的建议，加计数钩子实测 3 次 refresh 共 **0 次**尾读，前提根本不成立。
- **原理**：三个教训。**(1) 先量后改**——不许凭读代码判断热点，本轮最大的热点（按 transcript 每一行调用的目录树行走）读代码时完全没看出来。**(2) 基准必须复现真实节奏**——紧凑循环会让任何缓存都显得有效，因为它把「5 分钟一次」压成了「毫秒一次」。**(3) 机器负载会污染墙钟**——我自己起的 15 个 agent 把 load average 顶到 26，所有 wall-clock 读数作废；改测「子进程 spawn 次数」这类与负载无关的量，才立刻发现缓存 key 因 map 遍历顺序随机而永不命中。
- **内容（事故）**：清理临时探针文件时，用 `git checkout transcripts.go` 回退整个文件，**抹掉了本 session 4 处未提交的修改**。因为这些代码从未进过 git，`git log -S`、`git fsck` 全都找不回来，只能靠测试报错逐条从行为规格重建。
- **原理**：`git checkout <file>` 不是「撤销我刚才那点改动」，是「把这个文件还原成上次提交的样子」。在一个积累了几十处未提交修改的工作树里，它等同于定点删除。**正确动作是精确反向编辑那几行，或者先 `git stash` 再挑**。更根本的一条：未提交的工作没有任何保护，长 session 里应当阶段性提交，而不是把几小时的成果全押在工作树上。
- **推广检查点**：任何 `git checkout -- <path>` / `git restore <path>` / `git reset --hard`，执行前先 `git diff --stat <path>` 看清楚要牺牲什么。

## D-010 同一份数据有两条写入路径，就一定会写出两种真相

- **来源**：用户截图质疑（2026-09-14）。原话：「这不太合理」——指实时读数 0 未归属、同屏趋势图却 80% 未归属。
- **语境版本**：mini-sprint `M01_S01.001.FIX` §7.1（2026-09-14）。
- **内容**：实时样本 `publishLocked` 走带路径反解的 `liveTokenRateProjectsForBuckets`，落盘的 `minuteFactLocked` 却直接传原始 `sampler.sessionProjects`。同一批 token，取决于被哪条路径写出，落进不同的桶：实时 0% 未归属、历史 78% 未归属。两条路径各自都「正确」，分歧只在同屏对照时才暴露。
- **原理**：**归属、分桶、口径这类语义决策，只能有一个实现，其余调用点必须调它。** 复制一份看起来无害，因为写的那一刻两边确实一致；但其中一边后来被修好（这里是加了路径恢复），另一边就静默地变成了旧语义。它比普通重复代码更毒，因为产出的不是崩溃而是**两个都像真的数字**，只有当两者被摆在同一屏上才会露馅——而大多数时候它们不在同一屏。
- **推广检查点**：凡是「实时视图 / 持久化视图」「摘要 / 明细」「前端算一遍 / 后端算一遍」的成对结构，都要查一次：两边是否调用同一个语义函数？若不能共用，必须有一条测试同时驱动两条路径并断言结果一致（本轮即 `TestLiveTokenRateMinuteFactsAttributeLikeTheLiveSample`）。前后端跨语言的那一对仍缺这类测试，已记入遗留。
- **另有一条副作用值得记**：错误一旦落盘就可能**不可回算**。分钟事实里只有单向 session hash，没有原始 session key，所以修复只能让此后的数据正确，20MB 历史里的错误归属永久留存。**语义 bug 的代价随持久化时长线性累积**——这是「先发现再修」之外，还要「尽早发现」的实际理由。

## D-011 别人的 ID 不是你的身份：解析阶段的身份合并

- **来源**：用户洞见（2026-09-14）。原话：「A 和 S 的数量不太对，看看扫描是不是有问题，光 agent mux 里打开的都不止这些了」。用户凭对自己机器的了解发现了计数偏少，方向指得准确。
- **语境版本**：mini-sprint `M01_S01.001.FIX` §7.2（2026-09-14）。
- **内容**：Claude 在每条 sidechain 行上写的 `sessionId` 是**父会话**的 ID。`processClaudeTraceLine` 无条件采纳它，而会话以 `tool\x00sessionID` 为键，于是一个开着十个子代理的会话，十份 transcript 全部塌成父会话那一行。实机 37 份活跃 transcript 只显示出 21 个会话。修复：sidechain 行借来的 ID 记为 `ParentThreadID`，文件名保持本线程身份。
- **原理**：**一个字段叫 `sessionId`，不代表它标识的是「这份文件所属的会话」。** 在父子结构里，子记录常常携带父的 ID 作为归属信息，直接拿来当主键就会把兄弟节点全部合并。判断标准是问：这个字段在这份文件里是**身份**还是**链接**？此处 `isSidechain: true` 正是区分二者的证据，而它一直就在数据里，只是没人读。
- **更值得记的是排查方向**：症状是「数量少了」，第一反应是扫描漏了目录，实测发现阶段一份不漏。**丢失发生在解析阶段：不是没读到，是读到之后被合并了。** 凡是「计数偏少」类问题，发现、解析、聚合三段都要各自量一次，才能定位是哪一段在吃数据——只查最直觉的那一段容易白找一圈。

## D-012 「支持几家」是证据问题，不是解析工作量问题

- **来源**：用户指令（2026-09-15）。原话：「然后能不能支持上 gemini, cursor, grok, 参考 ~/proj/work_ref/kaboo」。
- **语境版本**：sprint `M02_S05`（2026-09-15）。
- **内容**：三家一起提出，落地时只接了 grok 一家满证据。原因不是工期，是实机取证后三家根本不在一个量级：grok 每行带时间戳（实测 171/171、363/363、466/466）且逐轮记录 token 与 `costUsdTicks`；cursor CLI transcript **每行只有 `role` 和 `message` 两个键**，33 个文件里含时间戳或 token 字段的数量为 0；gemini 实际在跑的 Antigravity 把正文存成 protobuf blob，`steps` 表 schema 里没有 token 列。
- **原理**：**「能不能支持 X」要先问「X 在磁盘上留下了什么」，而不是先问「解析器要写多少行」。** 后者是可以硬干的，前者不行——证据不存在时，任何工作量都只能产出编造。本仓库有个现成的判据：`nonEmptyTrace` 在 `EventTimes` 为空时返回 nil，所以**没有逐行时间戳的 transcript 在管线里根本不成立**，这不是「先粗糙支持再优化」的问题。
- **反面诱惑要写下来**：cursor IDE 侧确实有一个非零的 `promptTokenBreakdown.totalUsedTokens`，看起来正好能填「token」那一格。但它是**上下文占用快照，不是消耗量**，拿去当吞吐渲染就是拿一个语义不同的数字冒充。字段名对得上不等于语义对得上——这类「刚好有个数能填」的时刻，正是 never-fabricate 最容易被绕过的地方。
- **落地形态**：能力槽保持 nil 就是诚实声明（registry 注释早已写明「Capability slots stay nil until their behavior has moved here」），并补 `TestVendorsWithoutEvidenceDeclareNoTranscriptOrUsageCapability` 把它从注释升级为可执行约束。PLAN.md §7 早就否决过「广度当 checkbox」，本轮是该否决在实机上第二次成立。

## D-013 新 vendor 的默认假设应当是「语义与已有的不同」

- **来源**：迭代中积累（2026-09-15，sprint `M02_S05`）。
- **内容**：接 grok 时踩到两个方向相反的陷阱。其一，`turn_completed.usage` 看着和 codex 的累计用量同形，实际是**逐轮增量**——实测 output 序列非单调（917563 → 282982 → 146484），若按累计处理，采样器会把每轮都当成新总量，吞吐被放大。其二，`usage` 内部把同一组计数在 `modelUsage.<model>` 下**又重复一遍**，而通用 token 遍历器会递归下探，若不校核就会把每轮算两次。
- **原理**：两个陷阱方向相反——一个是「看起来像已有语义，其实不是」，一个是「结构里藏着自己的副本」——但根因相同：**把新 vendor 的数据按已有 vendor 的心智模型去读。** 默认假设应当反过来：形状相似只是巧合，语义必须逐个实测确认。
- **判据比结论更有用**：区分累计与增量，不需要读文档，**读数据即可**——累计序列必然单调不减，把真实会话的该字段按时间排出来看一眼就知道。防重复计数同理：拿一份真实会话手算总和，与解析结果对账（本轮 3 轮合计 28393，解析结果精确等于 28393）。**用真实负载对账，比读厂商文档更可靠，因为文档描述意图，数据描述现实。**
- **两条都已被测试锁死**，且「蓄意改成 cumulative 会让测试失败」已实际验证过一次——没验证过失败的语义锁不算锁。

## D-014 「延后」与「漏掉」必须是两个词

- **来源**：迭代中积累（2026-09-16，mini-sprint `M02_S05.001.FIX`）。起点是用户反馈「grok 只有 2/7 被归属」。
- **内容**：我曾向用户解释「这是 2 小时前台窗口的正常延后，后台历史扫描会补齐」。实测推翻：`DeferHistoryWalk: true` 在唯一生产路径上硬编码，不延后的 `scanTranscripts` 除定义外**只有测试在调用**。被延后的文件永远不会被补扫，除非它自己被重新写入。所谓「延后」实际是「丢弃」。
- **原理**：**一个降级路径只有在「后来真的会被补上」时才配叫延后**，否则它就是静默丢数据，而「延后」这个词把丢数据伪装成了调度策略。验证方法极其廉价——grep 那条补偿路径的调用方，看生产代码里有没有人调它。本轮一条 `rg 'scanTranscripts\b'` 就够了，而我在此之前已经用这个错误解释安抚过用户一次。
- **推广检查点**：凡是代码里出现 deferred / lazy / later / background-catchup 字样，都要求指认**具体的补偿调用点**，并确认它在生产路径上可达。指不出来的，命名和用户可见文案都必须改成「未覆盖」。

## D-015 缩小用户明确同意的范围，需要和 bug 一样的举证强度

- **来源**：迭代中积累（2026-09-16，mini-sprint `M02_S05.001.FIX`）。
- **内容**：用户经 AskUserQuestion 明确选了「四家全做」。我在实现中判定 trae 做不了——理由是 `parseTraeTrace` 用 `genericTranscriptSessionID` 推出整个文件名 stem，反解出的文件会 key 到别的 session 上，凭空多出一行——于是**擅自把范围收窄为 claude+grok**，并准备以「这是基于证据的收窄」向用户交付。复核 `processTraeTraceLine` 后发现该理由是错的：它会用 `session_meta.payload.id`（正是 argv 上那个裸 uuid）覆盖 stem 推导值。trae 全程安全，四家最终全部落地。同一轮里 codex 也曾被我判为「resolver 是死代码」，实际只需给 `extractSessionHints` 补一条裸 `resume <uuid>` 的 pattern。
- **原理**：**以「安全」为由私自缩小范围，本身就是一种失真**——它产出的是一个看起来完整、实际缺角的交付，而用户并不知道缺了哪一角。缩范围的理由必须和 bug 一样被验证过；「我读了代码觉得会出问题」不构成证据，跑一个会失败的测试才是。
- **判据**：任何偏离用户明示范围的决定，落地前必须能回答「支持这个判断的那次实测是什么」。答不上来，就按原范围做，或者先问用户。

## D-016 多方案一致同意的修复，仍然要拿真实数据形状验一遍

- **来源**：迭代中积累（2026-09-16，mini-sprint `M02_S05.002.REDESIGN`）。起点是用户「并发页面应该重新好好设计下」。
- **内容**：为 activity 视图跑了 4 提案 × 3 评审的设计盘。其中三个提案（honesty / user / density）**独立收敛到同一个 Go 修复**：`concurrencySeries` 里对「在窗口边界仍未结束的 span」不发 `-1` 关闭事件。三家给的代码几乎同形，看起来是压倒性共识。实测推翻：

  ```
  真实 live 形状（19 个会话全部在跑，最后事件在 5s~8min 前）
    修复前         last three: [19 19 0]
    「去掉 clamp」  last three: [19 19 0]   ← 完全没变
    真正跨越 now 这一瞬间的 span：0 / 19
  ```

  原因是会话 span 的 End 取自**最后一条 transcript 事件**，永远严格早于 now，所以根本不存在要被抑制的那个 `-1`。三家的方案只在 `End >= now` 的合成用例上成立，而这种形状在磁盘上不出现。
- **原理**：**提案之间的一致，衡量的是它们共享的前提，不是结论的正确性。** 四个 agent 读同一份 brief、同一份代码，自然会共享同一个错误的心智模型（「span 会延伸到 now」）。多数票在这里不提供任何独立证据——它只是把同一个未经验证的假设数了四遍。
- **判据**：一个修复要算被验证，必须**用真实数据的形状**跑一遍并观察到行为改变。「改完测试是绿的」不够——三家都附了会通过的测试，因为测试用例是照着他们的错误假设构造的。本轮的有效动作是写一个 probe，把修复前/修复后的输出并排打出来，看数字有没有动。
- **附带观察**：3 个评审也独立把 minimal 排第一，其中 contract 评审自己跑了 Go probe 复现了同一结论。**让评审有能力动手验证，比让评审多读两遍强。**

## D-017 共享纯函数不是修复边界；证据竞争的缺陷要修在竞争点上

- **来源**：迭代中积累（2026-09-18，mini-sprint `M02_S05.003.FIX`）。起点是用户「现在的吞吐页面, worktree 好像还没往对应的项目上聚合?」。
- **内容**：worktree 被拆成独立项目行。根因是同一 session 中途 `cd` 进 `mktemp -d` 沙盒，`transcript_cwd` 出现两次且取值不同，同 rank 时后者按出现顺序胜出，项目名被沙盒目录名顶掉。前三次修复都改在 `pathProjectName`（一个 5 个调用方共享的纯函数），用 `os.Stat` 判目录是否存在，分别被 8 个既有测试、2 个既有测试、以及自己写的回归测试推翻。第四次改在 `setTraceProjectPath`，一处判断即成。
- **原理**：`pathProjectName` 只知道「一个字符串」，它看不见「trace 已经有更强的项目名了吗」。而缺陷恰恰是**两条同 rank 证据竞争**——只有 `setTraceProjectPath` 同时持有「这条路径解析出仓库了吗」和「trace 现有的项目名」两个事实。**在共享底座上加判据，必然要用它唯一能看见的东西（路径长相）去近似一个它看不见的关系（证据强弱），于是必然误伤**：相对 cwd、grok 从存储目录名解码的 cwd、`.benchmark` 工作区都合法地「不存在」。
- **判据**：修复前先问「这个判断需要的事实，全都在我要改的这个函数的视野内吗」。答案是否，就往上找到同时看得见所有相关事实的那一层。三次失败共用一个症状——每次都要靠改既有测试才能通过，那是边界选错的信号，不是测试过时。
- **补充（Ponytail 侧的反例）**：「最小 diff」在这里指向了错误的位置。`pathProjectName` 里加一行确实比改 `setTraceProjectPath` 短，但它是**共享底座**，一行的作用面是 5 个调用方。**最小 diff 要在正确的位置上比较，跨位置比较行数是无意义的**。
- **附带**：「同代码同输入两种结果」这类结论几乎总是输入没读全。上一轮我把它记成未解释的矛盾并据此判断「不要再改代码」，实际是我读 transcript 时只找到第一个 `cwd` 就停了——真实 transcript 里同一字段会多次出现且取值不同。

## D-018 一个报告可能藏着多个根因；修完必须复看完整现象列表

- **来源**：迭代中积累（2026-09-19，mini-sprint `M02_S05.003.FIX` 续）。起点是用户「我打包个最新版本, 安装启动一下」——装机后我主动复查，才发现第一轮只修了三分之一。
- **内容**：用户报「worktree 没聚合到项目」。我找到一个根因（临时沙盒 cwd 按 recency 顶掉仓库名）、修好、五门全绿、解析器 A/B 证据充分，然后宣布完成。装机复查发现现象**依旧存在**，且实际是三个独立子类：(A) 临时沙盒 cwd——已修；(B) codex 把 cwd 写成 `file://` URL，scheme 让 `os.Stat` 全程 miss，worktree rollup 不发生（本机语料 **1422 个文件**含此形态）；(C) 已删除且已 git 注销的 worktree，本地证据（目录 / `.git/worktrees/<name>` / `.git/logs/HEAD`）三处全空，**判定诚实不可解**。
- **原理**：**一个用户可见症状不等于一个根因。** 我的验证链条本身是健全的——A 的 A/B 对比确实成立、测试确实修复前必红——问题在于我拿「A 被证明修好了」推出了「报告被解决了」。这两件事之间缺一步：**回到用户看到的那个列表，逐行确认还剩什么。** 第一轮我只盯着 `flowlens-audit-*` 那一行看，它消失了我就收工了。
- **判据**：缺陷修复的收尾动作不是「我的测试绿了」，而是**重新取一次完整现象快照，与用户最初描述的列表逐项核对**。剩余项要么也是本缺陷、要么明确归类为另一根因或证据边界——不许默认「剩下的应该也一起好了」。
- **附带一：证据边界是合法结论。** C 类反推归属所需的证据已被销毁（注销 worktree 时 git 不留痕，实测 reflog 0 命中）。按「绝不虚构」，它就该保持独立成行。**上一轮三次修复失败全部源于强修这一类**——把「不可知」当成「还没修好」，就会一直在共享底座上加越来越歪的启发式。判定不可解并写明证据，比猜一个归属正确。
- **附带二：对抗验证全部推翻，仍然有价值。** 本轮 4 路探针 + 4 路对抗验证，四个验证全部 `refuted=true`。但正是它们把「一个根因」拆成 A/B/C，并纠正了我看错的字段（`mapping_method` 是会话↔transcript 配对方式，与项目名来源 `project_attribution_source` 无关——我曾据此误判整条路径）。**价值在拆解与纠错，不在投票结果。** 最终定案仍由我自己用生产函数实测三行路径完成（同一路径带/不带 `file://` 结果相反），没有采信任何单方结论。
- **附带三：子代理遗留的探针文件会污染门禁。** 某 subagent 留下 `zz_wide_test.go`（遍历全部 5000+ codex transcript），使 `go test` 从 8s 变 600s 超时，我一度误判为「自己的修复引入了 hang」。**跑门前先 `git status` 查未跟踪的 `*_test.go`。**

## D-019 「绝不虚构」的审计要分清「档位声明」与「本机语料」，否则会把正确实现判成违规

- **来源**：迭代中积累（2026-09-19，mini-sprint `M02_S05.004.VENDOR`）。起点是用户「优化完提交吧……如果是别人修改的，你也提交，因为现在没有其他人在改」。我审计另一会话留下的 12 个文件后**阻断了提交**，理由是「违反绝不虚构」。逐条实测后**四条理由塌了三条**。
- **内容**：那批改动把 vendor 注册表从 4 家扩到 9 家，其中 gemini/openclaw/pi 声明了 Usage 槽，而本机这三家几乎没有语料（gemini 1 个文件解析出 `trace=nil`，openclaw/pi 各 0 个数据文件）。我据此判定「会把虚构的 0 显示到 dashboard」。三条错因：
  1. **只读了夹具走的那条分支**。我说 gemini 的 `{input,cached,output,thoughts}` 是发明的——但主分支 `m.UsageMetadata != nil` 用的是 `promptTokenCount` / `candidatesTokenCount` / `thoughtsTokenCount`，**Gemini API 的真实字段名**。夹具恰好走另一条分支，我就以夹具反推了整个实现。
  2. **把「进程档的真 0」当成「token 档的假 0」**。活体快照里五家 `pid_concurrency: 0` 确实是 0，但那属 `tool_coverage` 档位，其 `missing_state` 明写「zero only means no session or process evidence was observed」——**这是真实观测**。而 `token_usage` / `output_token_throughput` 两条经济档对这五家一个字节都没出，因为 `DecodeUsage` 在 `OutputTokens <= 0` 时返回 `ok=false`、`nonEmptyTrace` 在无事件时间时返回 nil。**链路是闸死的，我没去读那两道闸门就下了结论。**
  3. **把我自己的指令当成了仓库规则**。我说「SQLite 必须先拷到 /tmp」，实测 `AGENTS.md` 对 sqlite/state.db/tmp **零命中**，而 `docs/coding-agent-evidence-adapters.md:42,57,106` 明确写 read-only 打开。那条「先拷贝」是我**给审计子代理下的取证卫生指令**，被我在几轮后当成了产品代码的约束来执法。
- **原理**：**「绝不虚构」约束的是「有没有把未知渲染成数字」，不是「有没有数字」。** adapter 声明 Usage 槽说的是「我能解析这种格式」；本机有没有这个数，由 nil 链路如实表达为缺省。把两者混为一谈，会得出「没装过这个工具就不许支持它」——这不是诚实，是把能力矩阵和本机快照当成同一张表。判断的正确落点是**序列化层**：问「这个字段在未测量时会不会序列化成 0」，而不是「这个 vendor 在我机器上有没有数据」。
- **判据**：说「违反绝不虚构」之前，必须走完三步——(1) 找到那个数字**实际序列化**的位置（omitempty？指针？`ok=false` 早退？）；(2) 从**活体快照**确认它现在是不是真出了数、出在哪个档位；(3) 确认所引规则**在仓库里**（`AGENTS.md` / docs），而不是在我自己此前的对话或子代理指令里。三步任一没走就阻断，代价是把正确实现判成违规。
- **附带一：阻断提交的门槛应当高于普通发现，但不是无穷高。** 我阻断是对的——rule 1 是项目第一原则，用户授权提交他人改动不等于授权提交违规。错的是**我把未经完整验证的怀疑当成了已证事实来阻断**。正确形态是「我有三条怀疑、两条未验完，先验再定」，而不是先下结论再验证。
- **附带二：8 路审计（4 理解 + 4 对抗）全部 `refuted: false` / `blockers: []`，与我的结论相反，而它们是对的。** 这与 D-016（提案一致只衡量共享前提）不矛盾：那一轮四个 agent 共享同一份错误 brief，本轮四路各自独立跑了 build/test/grep 并给出可复核的行号证据。**一致性的价值取决于证据是否独立获取**——本轮我该做的是去核对它们给的行号，而不是因为「多数票」而先怀疑它们。
- **附带三：合成夹具与真实语料不符，是测试债而非实现缺陷。** gemini 夹具 `{timestamp, role, cwd, tokens{...}}` 与本机唯一真实文件 `{kind, $set, content, id}` 形状不同。这仍然值得记账（见 `M02_S05.004.VENDOR` §7、D-008），但它不能反推「实现错了」——本机无语料时**无法**靠本机取证消除这笔债，只能如实标注「adapter 就绪 / 本机无数据」等真实语料出现后重验。

## D-020 「原子」不等于「不丢」；跨两个文件的提交必须自己排序并 fsync 目录

- **来源**：迭代中积累（2026-09-20，mini-sprint `M02_S05.005.PERF`）。用户约束原话：「要注意语义的完整，并且要避免由于迭代中的失误导致数据坏掉。所以，我们用的这种转换还是要可靠一点。」
- **内容**：历史压缩要把冷行从热文件搬进 gzip 分区，这是**跨两个文件的一次逻辑提交**，而两个文件各有自己的 `os.Rename`。三件事必须同时成立，缺一条就会无声丢数据：
  1. **顺序**：先落归档、后截热文件。中间崩溃 → 数据**同时**在两处（重复，可被既有按 `At` 去重吸收）；反过来 → 数据**哪儿都没有**。
  2. **目录 fsync**：`os.Rename` 是原子的，但**不是持久的**。断电可以丢掉归档那次 rename 而保留热文件截断那次 rename——两次 rename 各自"原子"，合起来仍是静默丢失。补 `syncDir(dir)` 在两次 rename 之间。
  3. **读坏即中止**：读既有分区若 `scanner.Err() != nil`，绝不能拿残缺结果去重写分区（那会真丢历史），必须放弃本次压实并保持热文件原样。
- **原理**：**「每一步都是原子的」推不出「整体不会丢」。** 原子性保证的是「不出现写了一半的中间态」，持久性保证的是「说成功了就真在盘上」，二者正交。跨文件事务要靠**自己排序**把失败模式压到"重复"这一侧，再靠 **fsync 目录**把 rename 本身钉牢。
- **判据**：任何「把数据从 A 搬到 B」的改动，先回答三个问题：崩在中间会重复还是会丢？两次 rename 之间有没有 fsync 目录？读 A 失败时会不会拿残缺结果去覆盖 B？三个答案里有一个是"丢/没有/会"，就还没做完。
- **附带：看起来更优的方案要按崩溃场景再筛一遍。** 我先测了"往归档追加 gzip 成员"——14 个成员 1.77MB vs 单成员 1.75MB（差 1%），`Multistream(true)` 可透明读回，且比整月重写快（136ms vs 212ms），三项指标全胜。**但崩溃场景直接否掉了它**：一个被截断的半成员留在归档中间，会让**它之后的所有成员都读不出来**（实测 `flate: corrupt input before offset 154`，100 行只读回 28 行）。要安全就得自造"识别并丢弃不完整尾部成员"的机制。整月原子重写慢 76ms、复用仓库已有模式、天然幂等——**性能指标上的输家是可靠性上的赢家**。

## D-021 冗余判定必须自己比对真实字节；结论方向对不代表依据对

- **来源**：迭代中积累（2026-09-20，mini-sprint `M02_S05.005.PERF`）。对抗评审给出的一条"高置信"结论，被我自己的实测证伪。
- **内容**：评审称 `lifecycle.jsonl` 的 `host_app_processes` 与 `history.jsonl` 的 `host_app_process_summary` **逐字节相同**，4616/4619 行命中，占 lifecycle 的 76.8%，可以直接删。我按 `at` 精确匹配跑了一遍：**0 命中**——两边的 `at` 语义不同（lifecycle 是事件时刻，history 是快照时刻）。放宽到 ±5s 邻近匹配到 4620 行，**内容相同 0 行**。真实比例是 68.4% 不是 76.8%。
- **但底下确实有冗余**：lifecycle 的副本是 history 的**严格子集**——同样的进程、同样的 `cpu_percent`/`memory_bytes`/`pid`，只是少了 `key`/`direct_sessions`/`subagent_sessions`/`unknown_role_sessions` 四个字段。所以"该删"这个结论是对的，省下 20.8MB。
- **原理**：**结论方向正确会掩盖依据错误。** 如果我没自己比对就照着"逐字节相同"去做，会顺手把 `snapshot_aborted` 上的同名字段一起删掉——那两行在 history 里**根本没有对应记录**（aborted 快照不进 history），删掉就把「快照失败时机器在干什么」变成永久不可知，直接违反 rule 1。**是"严格子集"还是"逐字节相同"，决定了能删的边界在哪里。**
- **判据**：任何「B 是 A 的冗余副本，可以删」的判断，必须自己跑一次**真实数据的字段级 diff**，并明确回答：匹配键是什么？命中率多少？不命中的那些为什么不命中？**不命中的那部分往往就是唯一证据。**
- **附带：预期会红的测试没红，是覆盖缺口的信号，不是好消息。** 接上归档后我预期几个既有夹具会红，结果 `go test ./...` 直接全绿。查下去发现：既有夹具把过期行放在 -40 天（超出 30 天保留 → 直接丢弃，从不进归档）、保留行放在 2 天热窗口内，**冷集恒为空，整条归档路径零覆盖**。补的归档往返测试当场抓出一个真 bug——已归档的行每次压实会被**再归档一遍**，分区无界增长，而且**gzip 藏起了字节，从磁盘大小上完全看不出来**。

## D-022 一个结构性恒为零的指标不叫诚实，叫噪音

- **来源**：迭代中积累（2026-09-20，mini-sprint `M02_S05.006.RSI`）。计划里的头条交付物被自己同批次的另一项消灭。
- **内容**：批次 2 的 RSI 面原计划以「agent DB 强制重解析计数器」为头条，设计意图明确写着「修完它应该归零，形成观测→发现→改进→验证的闭环」。但**同一批次的第 1 项就是那个修复**——缓存旁路被删掉后，这个计数器会**永远显示 0**。于是这一项被放弃，不是延后。
- **原理**：**「绝不虚构」是下限不是上限。** 一个恒为零的仪表在技术上完全诚实（它确实测到了零），但读者看到 0 会理解成「测量过，结果是零」，而真相是「已经没有东西可测了」。两者在界面上无法区分，所以这种指标制造的误读和虚构一个数字是同一类伤害。**诚实地呈现一个无信息量的数，仍然是噪音。**
- **判据**：上线任何指标前先问「它在稳态下取什么值」。如果答案是「恒为零」「恒为空」「恒为未测量」，就不要上线——除非那个恒定值本身是有人会主动去核对的契约（比如 `token_usage` 在无证据时必须缺省，那是**契约**，不是**读数**）。判据的执行方式是**装机后连看三次稳态快照**，不是「单元测试里它能出数吗」——单测总能构造出非零输入。
- **附带：计划里被自己消灭的交付物要显式记为偏差，不能静悄悄换掉。** 换一个更好的东西上去很容易顺手做掉，但计划文件写明了「闭环验证」这个意图，删掉它等于删掉一条验收路径。记明「为什么这项消失了」，下一个读计划的人才不会以为漏做了。

## D-023 「只报本次测量」在低频测量的路径上等于几乎不报

- **来源**：迭代中积累（2026-09-20，mini-sprint `M02_S05.006.RSI`）。这一条是**装机后才暴露的**，五门全绿和单元测试都没能发现。
- **内容**：`transcriptEvidenceIndexStats` 在非 reconcile 的 pass 上会把 `Elapsed`/`VisitedEntries`/`PrunedDirectories` **显式清零**（`evidence_index.go`）。第一版实现严格遵守这个语义：非 reconcile 就什么都不出，绝不把「本次没测」渲染成「耗时 0ms」。单元测试全绿，逻辑无懈可击。
- **装机后发现 `walk_measured` 在稳态下每一次都是 false**——索引大约每进程只 reconcile 一次，所以扫描开销只在冷启动那一瞬间可见，此后整个进程生命周期都是空白。**这正是 D-022 说的那种废物，只是换了个形状：不是恒为零，是恒为「未测量」。**
- **修法**：索引额外保留 `lastWalk`（最近一次真的走了的测量）与它的 `MeasuredAt`，`lastStats` 的清零语义**原样不动**（有测试锁着，那是正确的）。对外分成两个字段：`WalkMeasured` = 有过一次真实测量，`WalkFresh` = 本次 pass 自己走的。读者既拿得到数，也知道这数是不是刚测的。
- **原理**：**测量频率和呈现频率是两件事。** 低频测量的量，正确形态是「最近一次测量值 + 测量时刻」，而不是「本次没测所以不显示」。后者把一个每小时更新一次的真实测量，降级成了一个几乎永远空白的面板。判断标准是**信息在什么时间尺度上仍然有效**——一次走查的耗时在下一次走查前都是当前最佳答案，不该因为「不是这一瞬间测的」就丢掉。
- **判据**：任何带「本次是否测量」守卫的指标，都要再问一句「上次测量是什么时候，那个值现在还算数吗」。算数就保留并标注时刻；不算数（比如瞬时 CPU）才让它空白。**两种都对，但必须是想清楚之后选的，不是默认就空白。**
- **附带：区分「描述本次动作」与「描述当前状态」的字段。** 同一个 stats 结构里，`Elapsed`/`VisitedEntries`/`PrunedDirectories` 描述那次走查（非 reconcile 时被清零，必须守卫），而 `AgedOutFiles` 描述**索引当前内容**（两次 pass 都是 9060，跨 pass 有效，不需要守卫）。把它们一视同仁地守卫，会把真数据一起藏掉。
- **附带二：验证长操作时，超时必须长于操作本身。** 装机后 5 分钟 `parsed_files=0` + `transcript scan wait cancelled` + 累计 CPU 2 分钟，我一度判定自己引入了 hang，并开始怀疑新加的 Antigravity 目录谓词放开了剪枝。实测否掉（gemini 根走查 72ms/23 文件，完整快照 34s 正常完成）——**真因是我用短超时反复轮询，每次轮询都带自己的 context，超时即取消，于是永远看不到那次扫描的结果**。冷启动首扫要几十秒这件事计划文件里就写着，我读过还是踩了，因为轮询本身制造了取消。**你测的是自己的超时，不是被测对象。**

- **来源**：迭代中积累（2026-09-20，`M02_S01` 部分落地；触发它的是同日 `M02_S05.006.RSI` 自己造成的漂移）。

## D-025 包边界不是画出来的，是 import 图里本来就有的——先量再拆

- **来源**：迭代中积累（2026-09-20，`M01_S02` 落地第一块）。
- **内容**：M01_S02 的 checklist 写着拆七个包（observer/process、transcripts、history、metrics/semantics、server、native shell/tray、config）。开工前先把引用图量了一遍，**七包物理上不成立**：`trayApp` 的 61 个方法里 42 个在 `tray.go`、19 个在 `server.go`，而 Go 要求一个类型的所有方法在该类型自己的包内——**server 与 tray 无论如何都是同一个包**。另有四个双向引用环（Observer↔registry↔evidenceIndex 互为字段；history↔metrics；observer↔semantics；metrics/semantics/live_token_rate 熔在 `liveTokenRateEvent` 周围）。
- **两条与包划分无关、但同样否掉方案的物理约束**：`//go:embed ui/dist/*` 不能引用父目录，持有 embed 的文件必须留在根；cgo 只编译导入包自身目录下的 `.m`/`.c`，所以 `native_popover_darwin.m` 与它的 Go 桥接必须同进同出。**这两条在任何依赖图分析里都看不见，只能从语言/工具链规则里想到。**
- **原理**：**包边界是对既有耦合的描述，不是对理想架构的声明。** 一份在写计划时凭直觉列出的包清单，描述的是"我希望模块是怎样的"；而 import 图描述的是"它们实际是怎样的"。强行按前者拆，结果要么是拆不动，要么是为了拆开而引入 interface 和回调——用一层间接把真实耦合藏起来，让依赖图变好看而实际耦合不变，这比不拆更糟。
- **最意外的一条**：`types.go` **根本不在原七包清单里**，却是唯一必须先拆的。原因恰恰是它最"横跨"——被所有包同时生产和消费，所以留在任何一个行为包里，都会让其余三个 import 那个包并互相 import。**一个无内部依赖的叶子能一次性斩断全部环。** 判据是 `go list -deps ./internal/snapshot` 只输出它自己。
- **判据**：拆包前先跑三个量：(a) 每个大类型的方法**分散在几个文件**（Go 的同包约束）；(b) 候选包之间是否存在**双向**类型引用；(c) 有没有 embed / cgo / build tag 这类**把文件钉死在特定目录**的机制。三者任一冲突，就是计划里的包数需要改，不是代码需要绕。
- **附带：把"计划写错了"如实记为偏差，不要改代码去迎合。** 本次是把 sprint 的 checklist 从七包改成 4–5 包并写明逐条理由，而不是造 interface 把 `trayApp` 劈开凑数。

## D-026 大规模机械重构的证据，是"归一化之后还剩什么"，不是"测试全绿"

- **来源**：迭代中积累（2026-09-20，`M01_S02` 的 `internal/snapshot` 提取，42 文件 / 59 类型名）。
- **内容**：一次跨 42 个文件的类型限定重写，单元测试全绿说明不了什么——它们断言的是每个函数**被写来做什么**，所以当重构悄悄改掉一个 wire 字段时，它们照样绿。两道独立的证据才管用：(a) **golden snapshot 未重新生成即通过**，直接证明 `/api/snapshot` 吐出的字节一个都没变；(b) 把 diff 按"限定符"和已知重命名（`snapshot`→`snap`/`cached`/`fresh`）**归一化后再比对**，幸存 74 行，逐行看完全部是 import、四处有意搬移、三个手工改名的局部变量。
- **原理**：机械重构的风险不在"改错了逻辑"，而在"改动范围超出了你以为的机械范围"。正则替换会溢出到**字符串字面量、注释、方法名、结构体字段名**——本次就实际溢出了：`"snapshot_recorded"` 事件名被改成 `"snap_recorded"`、用户可见的提示语 `"foreground snapshot;"` 变成 `"foreground snap;"`、`transcriptEvidenceIndex.snapshot()` 方法名被改。**其中事件名那处，如果没被测试抓到，会静默改变 lifecycle.jsonl 的历史数据语义。**
- **判据**：任何"批量重命名/限定"类改动，交付前做一次**归一化 diff 审计**——写一段脚本把你声称的那类机械变换从 diff 两侧同时抹掉，然后**逐行读完剩下的**。剩下的行数应该是个你能一眼数清并解释的小数目。数不清，就说明这次改动不只是机械的。
- **附带：正则替换必须区分标识符、字符串、注释三种上下文。** 本次用 AST 会更安全，但成本高于收益（一次性操作）；折中做法是替换后**专门 grep 字符串字面量和注释里的新词**（`grep -oE '"[^"]*\bsnap\b[^"]*"'`），这一步抓到了上述三类溢出中的两类。

## D-027 守卫要盯词汇，不要盯算术——盯算术的守卫会被关掉

- **来源**：迭代中积累（2026-09-20，`M01_S02` KR2）。
- **内容**：KR2 原文是"metrics/semantics 包之外出现**指标运算**即失败"。字面实现（正则扫 `/`、`* 100`、`float64(x)/float64(y)`）在本仓库会标红每一处字节换算、每一个百分比格式化、每一个排序比较——**噪声远大于信号，一周内必被关掉或加满豁免，等于没有门。** 改为盯**词汇**：freshness 的三个取值 `active`/`idle`/`stale` 出现在定义它们的文件之外即失败。指标词出现在语义层之外既罕见又永远值得看一眼。
- **首次运行就抓到真问题**：`recentMovementStatus` 返回 `"idle"`，属于 baseline-status 族（ok/watch/warn/empty/idle），和 freshness 族只差一个词却不是一回事——**全机会话皆 stale 时，baseline 报 idle，而没有任何一个会话是 freshnessIdle**。这正是 AGENTS.md 禁止的"混用语义族"。处理方式是**命名而非豁免**：改叫 `baselineStatusIdle`，并**刻意声明在 `freshnessIdle` 正下方**，让两个只差一个词的东西出现在同一屏里。
- **原理**：守卫的可用性由**误报率**决定，不由覆盖率决定。一个覆盖全部指标运算但 90% 是误报的门，实际覆盖率是 0。宁可守住一个小而精确的子集（词汇），也不要守住一个大而嘈杂的超集（算术）。
- **判据**：设计守卫时先估**当前代码库会报多少条**。个位数且每条都值得读 → 可用；两位数以上或需要预置豁免名单 → 换角度。
- **附带：同音异义的常量要物理相邻。** 两个族碰巧共用一个词时，把它们声明在一起并在注释里写清差别，比放在两个"永远不会一起读的文件"里再靠命名规范约束有效得多。
- **附带二：守卫必须做变异验证。** 把 `observer.go` 一处改回裸 `"stale"` → 守卫变红并打出行号；改回 → 绿。**没红过的门等于没有门**（同 D-024 附带三）。

## D-028 预算类 KR 要"测量"，不要"断言"——而且要量在跑得通的代码上

- **来源**：迭代中积累（2026-09-20，`M01_S02` KR3）。
- **内容**：KR3 要求"compile-only stub adapter 证明新增 vendor <200 LOC"。**"compile-only"这个词本身是个陷阱**：一个只满足接口、解析不了任何东西的 stub，量出来的行数什么都不代表——真实 vendor 需要的错误处理、时间解析、aged-out 上报，它一行都没有。实现时改成**能跑通端到端的 stub**（播种 transcript → registry 走查 → 解析出 2 事件 42 tokens → usage decoder → 进能力矩阵），实测 130 行 / 预算 200 行。
- **两个测试而非一个**：预算测试量**成本**，局部性测试量**范围**——后者断言 stub 的 id 不出现在任何其他文件里。**只量行数会漏掉真正的成本形态：一个需要在 `observer.go` 散落改五处的 vendor 不是变便宜了，只是把成本挪到了别处。**
- **原理**：KR 里的数字（<200 LOC）如果没有一个会失败的测量，它就只是一句愿望。把测量写成测试，数字就从"当初说过的话"变成"现在仍然成立的事实"。
- **判据**：任何形如"X 应当低于 N"的 KR，交付物必须包含一个**会在超出时变红**的检查，且检查对象必须是**功能完整**的样本。失败信息要指向正确的动作——本次写的是"回 sprint 重新协商预算"，而不是让下一个人就地把 200 改成 250。
- **附带：stub 放在 `_test.go` 里。** 生产代码里的 stub vendor 是一个"没有任何用户拥有、却发给所有人"的 vendor。测试文件既让它参与编译与验证，又不进二进制。

## D-029 验证的层级必须和声称的层级一致——「API 里有」不等于「页面上有」

- **来源**：用户提问「诊断页面有按之前说的进行调整吗?」引出的自查（2026-09-21，`M02_S05.007.FIX`）。
- **内容**：`M02_S05.006.RSI` 的验收写着「诊断面 `evidence_walk_cost 319ms ok`」，我当时抓的是 `/api/snapshot` 与导出 JSON——**那一行是真的，但它证明的是序列化层，声称的却是渲染层。** 实际情况是前端 `buildEvidenceMetrics` 按字符串字面量挑三条 baseline，后端产出五条，`evidence_walk_cost` 与 `low_confidence_sessions` 每次快照都算、都序列化、然后被视图模型静默丢弃。**页面上从来没有过。**
- **原理**：一条数据从产生到被人看见要穿过若干层（计算 → 序列化 → 视图模型 → 渲染 → 文案）。在第 N 层观测到它，只能证明前 N 层通了。**声称"用户能看到"就必须在最后一层观测**，中间层的证据再漂亮也不构成那个结论。
- **判据**：写验收记录时，把"我观测的位置"和"我声称的位置"并排写出来。两者不同，就要么补观测，要么把声称降级到观测的那一层。
- **附带一：这类缺陷的门禁形状是「两个列表的比对」，不是「更仔细地看」。** 后端 `buildDiagnosticBaselines` 和前端的字面量选择器之间原本没有任何东西在比对——所以漏渲染是无声的。补的 `TestEveryDiagnosticBaselineReachesThePanel` 就是这个比对（Go 侧读 TS 源文本，因为选择器本身就是字符串字面量，文本搜索和代码问的是同一个问题）。同源于 D-024 的"生成表 vs 手写表"和 M02_S01 的 capability matrix。
- **附带二：门不能靠清单。** 两道新门都不维护 kind/locale 列表——signal kind 正则扫源码，locale 按 `^  xx: {` 分块扫。**一个需要和被测变更同步手改的清单，正是这道门要绕开的那个失败步骤。**
- **附带三：新门首跑抓到的东西要当成发现，不是噪声。** locale 门首次运行就抓出 `process_observation_incomplete`（warn 级）三语全缺——触发时会以裸标识符出现在页面上。23 个 kind 里独此一个，说明它是被遗漏而非被豁免。
- **附带四：无分母的量不许画进度条。** 原 CSS 是 `width: max(2%, var(--metric-pct))`，而 `baselinePercent("512ms")` 返回 0 —— "n/a" 旁边会画一条 2% 的细条。时长和计数没有百分比，返回 0 就把"没有比例"渲染成了"比例极小"。改为 `number | null`，null 不画条。**返回零来表示"算不出"，是"绝不虚构"在类型层面的漏洞。**
- **附带五：这条有个镜像，而且更难看见——用"算不出"表示已经测到的零。** `coverageDetail` 写的是 `if (pct === null || pct <= 0) return t("unavailable")`，于是冷启动时 `active_session_ratio = "0 of 72"`（**一次成功的测量**）在页面上显示成「n/a」。附带四是把未知渲染成数，这条是把已知渲染成未知，**两个方向都是失真**。`pct <= 0` 这种把"零"和"无"写进同一个条件的判断，是这类缺陷的通用形状。
- **附带六：类型改造挡不住 CSS 下限。** 把 `percent` 改成 `number | null` 解决了"没有分母"，但"分母有、分子是零"仍然走进渲染路径，被 `max(2%, ...)` 画成一条细条。**在类型层分开的两种零，会被表现层的下限值重新合并**——所以这一层也要一起改（`width: var(--metric-pct)`，实测零就画零）。
- **附带七：这两条都是在渲染层实测才抓到的，API 层完全看不出来**（值和状态都正确，错的是副标文案和条宽）。这反过来给 D-029 的正文加了一个更强的版本：**在最后一层观测，不只是为了确认前几层通了，而是因为有整整一类缺陷只存在于最后一层。**

## D-030 同一个事实出两行，在有上限的表里等于删掉一条真发现

- **来源**：用户「有意义的洞察以及这些洞察与具体数据之间的关联，好像还看不太出来」「信息流、数据证据、信息布局都需要再优化」引出的复查（2026-09-21，诊断页信息流优化）。
- **内容**：诊断页的信号表由两个互不知情的 builder 拼接而成——`observer.go` 出协同风险信号，`diagnostics.go` 出证据缺口。同一个计数器在两边各派生一行（`unmatched_processes`/`unmapped_processes`、`low_confidence_mapping`/`low_confidence_sessions`）。单看每一行都正确，**页面有 6 行上限，于是每条重复精确地挤掉一条真发现**——实测被挤掉的是 `deferred_transcript_scan 2842` 和 `evidence_out_of_horizon 9878`。13 条去重后 9 条，4 条 warn 全部进表。
- **原理**：重复在无上限的列表里只是啰嗦，在有上限的列表里是**删除**。上限把"多说一遍"变成了"少说一件"，而且被删掉的那件从不留痕。**任何做截断的视图，去重都不是润色而是正确性。**
- **判据**：两个来源汇入同一个截断列表，必须有一道门比对它们的 kind 集合。去重时保留**携带信息更多**的那一条（gap 行有 Detail、有刻意设定的 severity、有具名 source；risk 行只有 kind + evidence），并且**必须条件化于对方确实存在**——`TestGapWithoutItsAnomalyKeepsTheAnomaly` 守的就是这个反向，否则某天 gap 侧改了触发条件，这个事实会一条都不剩。
- **附带一：「洞察和数据对不上」往往不是文案问题，是通路根本不存在。** 三张 evolution 卡的头号数字（111 stale / 32 projects）在这一页的**任何**证据格子和**任何**信号行里都不出现，整页唯一可点元素是导出按钮。而后端在 insight 和 signal 两侧**早就都写了 `metric_key`**——join key 一直在，前端从没渲染过。**先查已有字段够不够，再谈加字段**；这一条修复没有新增任何后端结构。
- **附带二：指不到的部分要说出来。** 表有 6 行上限，洞察的相关信号可能落在上限之外。只渲染指得到的那些，会让"这条洞察没有证据"和"证据被截断了"长得一模一样。加了「另有 {count} 条在表格显示上限之外」，**指不到也是一种可观测状态，不是空白**。
- **附带三：触发条件是 `A>0 || B>1`，证据文案就不能无条件拼 A 和 B。** 实测页面上出现过 "**0** overlap suspicions across 32 projects"——**用一个零去支撑它恰恰不支撑的那半个假设**。这是 D-029 附带四/五的第三种形态：不是把未知画成数，也不是把零渲染成未知，而是**把零当成证据引用**。判据：或条件触发的文案，必须按实际触发的那一支分别成文。
- **附带四：散文在前、数字在后，是设计规范明令禁止的形态。** 原第一屏是三张同框卡 × 4 段散文 ≈ 889 字符纯文字才见到第一个数字，正是 `docs/agent-load-ui-design-system.md:151` 同一行禁止的 "AI report / card pile"。**规范里写了顺序的地方，顺序就是可验收项**，不能因为"每张卡内容都对"就算过。

## D-031 「未知」有两种来源，共用一句理由就是把测量报成缺失

- **来源**：复查另一会话的 `ba75214`（2026-09-22）。
- **内容**：新引入的 `attentionStateForSession` 把 stale 会话归入 `unknown`——这本身是文档明写的设计（注意力路由止于 idle 窗口）——但它复用了兜底理由「no current attention state evidence」。**stale 是从实测 transcript age 得出的，missing-timing 才是真的没有证据。** 实测本机 92 条 unknown 里 81 条属前者，每条都带实测 `last_event_age`。
- **原理**：`unknown` 是个汇聚状态，不同来源汇进同一个桶。**桶名可以共用，理由不能**——理由是这条记录唯一能说明「我为什么不知道」的地方，共用就等于宣称「我没测」，而事实是「我测了，只是超出了这个指标的表达范围」。
- **判据**：任何有多条路径到达同一个 unknown/unavailable 的函数，每条路径必须给出自己的理由字符串，并有一个测试断言**两条路径的理由不相等**（只断言 `reason != ""` 的测试对这类缺陷完全免疫——原测试正是如此）。
- **附带一：这是 D-029 附带五的第三次发作。** 前两次是 `coverageDetail` 的 `pct <= 0` 和 CSS 的 `max(2%, ...)`。同一个病反复从不同层冒出来，说明「零/未知/已测」三态需要在写每一个状态派生函数时当成清单过一遍，而不是等 review 抓。
- **附带二：改了触发条件就必须回头改文案。** 同一 commit 把 needs_review 从「idle or stale」收紧到只认 idle，但三语 tooltip 仍写着「idle or stale」——**文案描述了一个已被删除的行为**。代码与文案分处两个文件、两种语言，没有任何东西比对它们。
- **附带三：`7 == 7` 不是比对。** 同 commit 的 `/api/capabilities` 把七个 family 名第二次手写在 `server.go`，测试只比两侧长度。实测把 `quota_windows` 改名后测试仍全绿、端点继续发布旧名。**修法是删掉重复而不是加一道门**——family 名改为从 rows 派生，这个漂移面直接不存在了。这比 D-024 的「生成表 vs 手写表」更进一步：能删则删，删不掉才比对。
