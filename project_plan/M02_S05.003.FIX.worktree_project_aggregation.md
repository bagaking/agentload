# M02_S05.003.FIX — worktree 项目聚合

## 1. 用户原话

> 现在的吞吐页面, worktree 好像还没往对应的项目上聚合?

## 2. 三个子类，两个根因，一个诚实不可解

装完第一版修复后复查，发现问题只解决了一部分。完整分类：

| 子类 | 现象 | 根因 | 结论 |
|---|---|---|---|
| **A** 临时沙盒 | `flowlens-audit-bea26d8c.RjqnPR` 独立成行 | 中途 cd 进 `mktemp -d`，同 rank cwd 按 recency 覆盖 | **已修**（§3）|
| **B** `file://` cwd | `flowlens-v2-budget-roster-release-exact-260918` 等**同时**作为 worktree 挂在 flowlens 下、又独立成一行 | codex 把 cwd 写成 `file://` URL，`os.Stat` 全程 miss | **已修**（§4）|
| **C** 已删除且已注销的 worktree | `flowlens-v2-analysis-cost` 等独立成行 | 目录没了、git 也注销了，本地无任何证据可证其归属 | **诚实不可解**（§5）|

B 的判别特征很关键：**同一个名字同时出现在两处**——既是 flowlens 的 worktree 子项，又是顶层项目行。这说明 worktree 链路解析成功过，只有项目名那一路失败了。

## 3. 根因 A：同一 session 中途 cd 进临时目录

实读真实 trae transcript（`~/.trae/cli/sessions/2026/09/18/rollout-…-01a0b175-….jsonl`），同一个文件里出现**两个不同的 cwd**：

```
line 3253  cwd = /Users/…/workspaces/flowlens/flowlens-v2-analysis-cost
line 3262  cwd = /tmp/flowlens-audit-bea26d8c.RjqnPR
```

agent 先在 worktree 里工作，中途 `mktemp -d` 出一个按 git SHA 命名的审计沙盒并 `cd` 进去。两个 cwd 都以 `transcript_cwd`（rank 4）上报，`setTraceProjectName` 只拒绝**更低** rank 的覆盖，同 rank 按**出现顺序**后者胜 → 项目名变成 `flowlens-audit-bea26d8c.RjqnPR`。

**这解释了上一轮那个「无法解释的矛盾」**（探针解析正确、app 解析错误）：并不矛盾。探针只喂了一个 cwd，app 喂了全部。同代码、同路径、**不同输入**。上一轮把它记成「同输入两结果」是我读少了——只找了第一个 cwd 就停了。

修复（`setTraceProjectPath`）：**仓库无主的临时目录 cwd 不得顶掉已归属的项目名**。

```go
scratchOverwrite := repoRoot == "" && isGenericTemporaryPath(path) &&
    trace != nil && trustedTraceProjectName(trace.Project) != ""
if !scratchOverwrite { /* 才允许写项目名 */ }
```

`isGenericTemporaryPath` 是**既有**函数（`configRootProjectAttribution` 已在用同一概念）。三个约束条件各有必要，缺一即误伤：

- `repoRoot == ""` — `/tmp` 下的真仓库正常解析，不受影响
- `isGenericTemporaryPath(path)` — **活体验证抓到的回归**：第一版只判「无仓库」，把 `~/.agentmux/scratch/topic--launcher--<uuid>`（真实存在的非 git 工作目录）也挡了，它本来在纠正一个从存储路径猜出的垃圾名，挡掉后 4 行 UUID 尾巴垃圾名回归
- `trace.Project != ""` — 临时目录仍可能是唯一证据，全程只在 `/tmp` 里跑的 session 照报（「绝不虚构」：这时报出来是诚实的，报 unassigned 反而丢信息）

## 4. 根因 B：codex 的 cwd 是 `file://` URL

**这一条是并行调查（4 路探针 + 4 路对抗验证，8 agent）查出来的，四个对抗验证全部推翻了各自的探针**，最终由我自己用生产函数实测定案。

三行实测把事情说清楚（`resolveRepoBoundary` + `setTraceProjectPath`，真实路径）：

```
/Users/…/workspaces/flowlens/flowlens-v2-budget-roster-release-exact-260918
  → root="…/larkvc/flowlens" wt="flowlens-v2-budget-roster-release-exact-260918"
  → Project="flowlens"                                    ✓ 正确聚合

file:///Users/…/workspaces/flowlens/flowlens-v2-budget-roster-release-exact-260918
  → root="" wt="" br=""
  → Project="flowlens-v2-budget-roster-release-exact-260918"   ✗ 只差 7 个字符的 scheme

/Users/…/workspaces/flowlens/flowlens-v2-analysis-cost   （目录已删）
  → root="" → Project="flowlens-v2-analysis-cost"          ✗ 子类 C
```

机制：codex 把工具调用 payload 里的 cwd 写成 `file://` URL，而 cwd 提取走的是整行字节扫描（`jsonStringField` 取行内第一个 `"cwd"`），于是 URL 形态的 cwd 被喂进归属链路。`walkRepoBoundary` 对字符串 `file:///Users/...` 做 `os.Stat(…/.git)` 必然全程 miss，worktree rollup 不发生，`filepath.Base` 拿到 worktree 目录名。

**普遍性已实测**：本机 codex 语料里 **1422 个文件**含 `"cwd":"file://`。不是个例。

修复（`setTraceProjectPath` 入口一行 + 一个小函数）：

```go
path = localPathFromFileURL(path)   // file:// → 本地路径；非 file URL 原样返回
```

放在 `setTraceProjectPath` 是因为它是**所有 cwd 归属的唯一漏斗**（codex / opencode / grok / extra transcripts 全部经此），一处修全部受益；且必须放在 `resolveRepoBoundary` **之前**，这样 worktree/branch 也一并恢复，不只是项目名。

用 `url.Parse` 而非 `TrimPrefix`：要正确处理 `file://localhost/...` 与 percent-encode（`%20` 之类若不解码会带进 `filepath.Base`）。同时**拒绝**非空非 localhost 的 host（`file://server/share` 是远端 UNC，本进程无从解析）和非 file scheme。

## 5. 子类 C：判定为诚实不可解

已删除且已 git 注销的 worktree（`flowlens-v2-analysis-cost` 等），实测本地已无任何证据：

- 目录不存在；祖先目录无一持有 `.git`（全是 farm 分组目录）
- `<main>/.git/worktrees/<name>/` **不存在**（注销即删除，不留痕）
- `<main>/.git/logs/HEAD` grep 该名字 **0 命中**

**按「绝不虚构」，这一类应当保持独立成行。** 反推它属于 flowlens 需要的证据本地已被销毁，猜一个归属就是虚构。这不是「没修完」，是**证据边界**。

上一轮三次尝试失败正是因为想强修这一类，全都改在 `pathProjectName` 并用 `os.Stat` 当判据：

| 尝试 | 被什么推翻 |
|---|---|
| 1 | 扫 `<main>/.git/worktrees/*/gitdir` 反查——需要仓库注册表，机制过重；且现已实测该目录注销后并不存在，方案根本不成立 |
| 2 | `os.Stat` 失败即拒绝 → **8 个既有测试失败**（相对路径 fixture 磁盘上从不存在）|
| 3 | 收窄为「绝对路径 + 全部祖先都不存在」→ 自己的回归测试也失败（`/tmp` 永远存在）|

## 6. 教训（记入 OPINIONS）

1. **`os.Stat` 无法区分「已删除的临时 checkout」和「本就不该 stat 的路径」**（相对 cwd、grok 从存储目录名解码的 cwd、`.benchmark` 工作区）。
2. **修复边界要选在「同时看得见所有相关事实」的那一层**。`pathProjectName` 只知道一个字符串，看不见「trace 已有更强项目名吗」；缺陷恰恰是两条同 rank 证据竞争。改共享底座（5 个调用方）必然误伤，改竞争点一次就成。**「最小 diff」要在正确的位置上比较，跨位置比较行数无意义。**
3. **「同代码同输入两种结果」几乎总是输入没读全。** 上一轮据此判断「不要再改代码」，实际是我读 transcript 只找到第一个 `cwd` 就停了。
4. **一个报告里可能藏着多个根因。** A 修完我以为结束了，装机复查才发现 B 和 C。**修完必须复看完整现象列表，不能只看目标那一行。**
5. **对抗验证推翻探针，不等于探针没价值。** 本轮 4 个验证全部 `refuted=true`，但正是它们把「一个根因」拆成了 A/B/C 三类，并指出 `mapping_method` ≠ `project_attribution_source`（我原先看错了字段）。价值在拆解，不在投票结果。
6. **子代理留下的探针文件会污染门禁。** 本轮一个 subagent 遗留 `zz_wide_test.go`（遍历全部 5000+ codex transcript），让 `go test` 从 8s 变成 600s 超时，一度被我误判为「修复引入了 hang」。**跑门前先 `git status` 查未跟踪的 `*_test.go`。**
