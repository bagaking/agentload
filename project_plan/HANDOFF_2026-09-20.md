## 3. 这个项目最容易踩的坑（都踩过，别再踩）

这些不是抽象建议，每条背后都有一次真实事故。完整版在 `CURRENT.md` §4「质检步骤库」，这里只列最致命的：

1. **`go:embed ui/dist` 意味着在跑的进程永远拿不到新的前端产物。** 改 UI 必须重建二进制并重装，只跑 `vite build` 什么都不会变。
2. **冷启动首扫要几十秒。** 用短超时轮询会让每次轮询自带的 context 超时即取消，于是永远看不到结果——**你测的是自己的超时，不是被测对象**。我因此误判过一次"自己引入了 hang"。（D-023）
3. **跑门禁前先 `git status` 查未跟踪的 `*_test.go`。** 某次 subagent 留下的探针文件遍历 5000+ transcript，把 `go test` 从 8s 拖到 600s 超时。
4. **上线任何指标前先问它在稳态下取什么值。** 「结构性恒为零」和「结构性恒为未测量」都会被读成"已测量且为零"，比不上线更糟。判据是**装机后连看三次稳态快照**，不是单元测试能不能构造出非零。（D-022 / D-023）
5. **说某处"违反绝不虚构"之前走完三步**：找到它实际序列化的位置 → 从活体快照确认它现在出不出数 → 确认所引规则在仓库里而不是在对话里。我跳过这三步，把一个正确实现判成了违规。（D-019）
6. **冗余判定必须自己跑真实数据的字段级 diff。** 一个二手结论说两份数据"逐字节相同"，我实测是"严格子集"——差别决定了能删的边界在哪里，照着错依据删会毁掉唯一证据。（D-021）
7. **「预期会红的测试没红」先当覆盖缺口查，不是好消息。** 一次全绿掩盖了归档路径零覆盖，补测试当场抓出真 bug。
8. **改了 adapter 能力槽或证据根，必须跑 `go test . -run TestCapabilityMatrixDocMatchesTheRegistry`。** 这是新加的发布门。

## 4. 安全红线（**读之前先看这条**）

- **绝不读** `~/.cursor/cli-config.json`、`~/.grok/auth.json`、任何 `state.vscdb`。里面是**活的** OAuth token、API key、userId、邮箱。
- **grok 把整个用户 prompt 塞在 argv 的 `--` 之后**，实测观察到的真实 prompt 里含**活的 OAuth refresh token、API key 和邮箱**。`sanitizeCommandForClient` 负责脱敏，`process_test.go:502` 与 `server_test.go:1214` 钉着它。**任何抓 argv 的东西都会抓到密钥。**
- 调查时**绝不整份打印文件内容**——只提取字段**名**、key 集合和**计数**。报形状，不报值。绝不打印 prompt 正文，绝不打印 argv。
- 自己调查 SQLite 时先复制到 `/tmp` 再打开（这是**调查卫生**，不是仓库规则——产品里的 adapter 按设计就是原地只读打开，`docs/coding-agent-evidence-adapters.md` 明确背书，别把它当违规报上来）。
