# M02_S05.001.FIX — 活跃 session 的 transcript 反解

## 1. 背景与用户原话

用户看到 popover 里 grok 只有 2/7 会话有归属，问「所以是要优化是吧？那你继续优化呗」。
随后通过 AskUserQuestion 确认两项范围决定：**(1) 归属 bug 与 `deferred_files` 低报一起修；(2) 四家 vendor 全做**。

## 2. 先更正一处我对用户的错误解释

此前我告诉用户「这是 2 小时前台窗口的正常延后，后台历史扫描会补齐」。**这句话是错的，已由实测推翻**：

`DeferHistoryWalk: true` 在唯一的生产路径上硬编码；不延后的 `scanTranscripts` 除定义外**只有 `*_test.go` 在调用**。
所以被延后的文件**永远不会被补扫**，除非它自己被重新写入从而回到窗口内。这是漏数据，不是延后。

记入 OPINIONS D-014。

## 3. 根因（实测，非推断）

活跃 session 的 transcript mtime 与归属状态严格对应。修复前 03:14 基线：**claude 26/36、codex 21/22、grok 4/7**，13 个未归属 session 磁盘上**都有** transcript。

代码里**已经有**绕过 cutoff 的通道：priority 文件在 `collectTranscriptCandidatesWithCoverage` 与 `currentSnapshot` 两处都跳过 mtime 过滤。但 priority 只来自 `process.SessionFiles`，而它由 **lsof** 填充——实测 lsof 对本机 47 个 agent 进程几乎拿不到有用结果：

- grok 持有的是 `events.jsonl`，**不是**我们解析的 `updates.jsonl`；
- claude append-then-close，**一个 .jsonl fd 都不常驻**。

而 argv 里明明有 session id：`extractSessionHints` 早就解析出来了，却只被当作弱 fallback 的 map key，从未用来定位文件。

**修复 = 把已解析的 session id 反解成磁盘路径，喂进已存在的 priority 旁路。** 不新增机制。

### 为什么不是「把窗口调大」

实测全量 stat-walk：claude 7.0s、codex 2.4s、grok 1.6s。按 id 定向 glob 则是毫秒级。差两个数量级。

## 4. 实现

### 4.1 per-vendor resolver（沿用既有惯用法）

`builtinProcessIdentity` 上新增可选 nil-able 字段 `transcriptForSessionID` + nil-guard 访问器 + registry 委派——与 `sessionIDHint` / `rootFromTranscript` 完全同形。**不新增 `agentCapabilities` 槽位**（那四个槽位表达「有无证据支持」，由 `TestVendorsWithoutEvidenceDeclareNoTranscriptOrUsageCapability` 守住）。

| vendor | glob |
|---|---|
| claude | `<root>/projects/*/<ID>.jsonl` |
| codex | `<root>/sessions/YYYY/MM/DD/rollout-*-<ID>.jsonl` + `<root>/archived_sessions/rollout-*-<ID>.jsonl` |
| trae | `<root>/cli/sessions/YYYY/MM/DD/rollout-*-<ID>.jsonl` |
| grok | `<root>/sessions/*/<ID>/updates.jsonl` |

**绝不虚构的落点**：resolver 只返回 `filepath.Glob` 真实命中的路径，绝不拼接未经验证的路径；session id 必须匹配裸 uuid 形状（live codex 命令行里混有 `fco_…`/`msg_…`/`call_…`，globbing 这些可能误中无关文件）。由 `TestTranscriptForSessionIDDoesNotInventPaths` 锁死。

### 4.2 uuidv7 日期收窄（codex/trae 的关键优化）

codex/trae 的 session id 是 uuidv7，其内嵌时间戳**就是**文件所在的日期目录——本机 5275 个 rollout 全部吻合，**0 例外**。据此把 `YYYY/MM/DD` 从通配收窄为定值：

- 收窄前：33 个 id 跨 2253 个目录 → **913ms**
- 收窄后：同样 33 个 id、同样命中 12 个 → **20.3ms**（45x）

非 v7 的 id 退回通配 glob，而不是解析成一个错误日期。

### 4.3 argv 形态补齐

`extractSessionHints` 原先只匹配 `--resume`，但实机上 codex/trae 用的是裸子命令 `codex resume <uuid>`（24 个进程）。新增一条锚定完整 uuid 的 pattern——锚定是必要的，否则 `resume` 后面任何词都会被当成 session。

### 4.4 priority 文件改走 tail 解析

原先 priority 强制**全量** `Parse`。被恢复的文件里最大的一个 **133MB**，每次 append 都全量重读不可接受。改为：priority 永不 deferred，但已静默的走 tail——session 是活的，近期事件足以定位它。

### 4.5 `deferred_files` 口径（本轮两次修正）

根因是延后时把 `collectionCutoff` 塌缩成 `ForegroundCutoff`，老文件在收集阶段就被丢掉，从未进入计数。改为收集阶段恒用 `HistoryCutoff`，把「老于前台窗口」的判定交给**已经存在**的 `deferred` 标记。

**过程中我把计数放错了三次**，都由实测数字戳穿：

1. 放在 index 过滤点 → 恒为 0（索引本就按塌缩后的 cutoff 建）
2. 放到 walker → 仍为 0（`discoverTranscripts` 手抄字段，把新增的 `AgedOutFiles` 悄悄丢了；改用 `result.merge`）
3. 加上 walker 的 `AgedOutFiles` → **11043**，而独立统计只有 **2826**。原因：walker 的 cutoff 是 7 天**历史地平线**，被它排除的文件是**范围之外**，不是覆盖缺口。把「超出观测范围」报成「我漏了」同样是虚构。

最终口径：**只有索引内（即 7 天内）被前台 cutoff 挡下的文件算 deferred**。实测 2879，与独立统计 2826 吻合（差值为运行期间的文件漂移）。

`ScannedFiles` 同步改为「本轮真正读过的文件数」，否则会被膨胀成整个候选集。

## 5. 验收

### 5.1 四门 + 语义门

`go vet ./...` 绿；`go test ./...` 绿；`npm --prefix ui run build` 绿；`node scripts/validate_locales.js` 绿；`./build_macos_app.sh` 绿。

### 5.2 实机归属（同一台机器，新旧二进制并行对照）

| vendor | 修复前 | 修复后 |
|---|---|---|
| claude | 10/19 | **17/18** |
| codex | 26/26 | 23/23 |
| grok | **2/6** | **6/6** |

（会话总数随进程起落而变，故用比例对照。）

### 5.3 性能（进程内实测，三趟）

| | 冷启动 | 热态 |
|---|---|---|
| 修改前 | 13.61s | 0.55s / 0.45s |
| 修改后 | 14.06s | 0.52s / 0.46s |

**扫描本身如实计数不额外花钱**。

HTTP `/api/refresh` → 新快照的端到端耗时另测三轮：旧 0.55s / 0.55s，新 0.79s / 0.82s，**稳定高出约 0.25s**。这部分不在扫描里，合理归因是新二进制归属出更多会话、快照体积变大导致的 sanitize + 编码开销；未逐项拆解，**记为已知的小幅回退**而非「无影响」。绝对值仍远低于刷新节拍，暂不优化。

注意首轮测到的 67s / 139s **不是**性能数据，是 **refresh slot 量化**造成的等待——`requestRefreshForSlot` 在 slot 未变时直接 no-op，默认 slot 为 300s。这一点差点让我把正常行为误判成严重回归；对照实验必须显式传 `interval_ms`。

### 5.4 回归锁

- `TestRootsFromLiveProcessesResolvesTranscriptsFromArgvSessionID` — 四家齐备，`SessionFiles` 为空 + argv 带 id（**这正是真机状态**）。
- `TestTranscriptForSessionIDDoesNotInventPaths` — 四家 × (uuidv7 收窄路径 / uuidv4 通配路径)，磁盘无文件时必须返回 false。
- `TestDeferredCountIncludesIndexedFilesAgedOut`、`TestForegroundTranscriptScanCanDeferHistoryWalk` — 计数口径。

## 6. 有意变更的既有断言

- `TestForegroundTranscriptScanDefersOlderNonPriorityFiles`：full=1/tail=1 → full=0/tail=2（priority 改走 tail）；`ScannedFiles` 3 → 2（改为「真正读过的」）。
- `TestForegroundTranscriptScanCanDeferHistoryWalk`：`DeferredFiles != 0` 曾把**低报锁成预期行为**，现改为 1。
- `TestForegroundTranscriptScanDefersFreshMTimeWhenTailIsOlder`：`ScannedFiles` 1 → 0。

## 7. 一处被我自己推翻的判断（记录以免重犯）

我一度判定「trae 不能做，因为 `parseTraeTrace` 用 `genericTranscriptSessionID` 推出整个文件名 stem，反解出的文件会 key 到另一个 session 上，凭空多出一行」，并据此**擅自把范围收窄成 claude+grok**——而用户明确选的是「四家全做」。

复核 `processTraeTraceLine` 后发现该判断是错的：它会用 `session_meta` 的 `payload.id`（**就是 argv 上那个裸 uuid**）覆盖掉 stem 推导值。trae 完全安全。四家已全部落地。

教训：**以「安全」为由私自缩小用户明确同意的范围，本身就是一种失真**；缩范围前必须像验 bug 一样验证那个理由。记入 OPINIONS D-015。
