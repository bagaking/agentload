# M02_S01 · 证据覆盖矩阵：UI / API / 文档三端同源

## OKR

- **Objective**：把"诚实分级"从文档原则变成可执行的机器事实——任何能力变化在三端零手工同步。
- KR1：改一处 adapter 能力声明，API、UI 面板、文档页三端同步更新（测试证明零手工编辑）。
- KR2：100% 渲染的 snapshot 数据可追溯到某个矩阵 cell 及其命名的证据来源。
- KR3：审计测试证明未观测 cell 渲染为带标注的空缺——绝无零值、估算或推断的假对等。

## Checklist

- [x] 从 M01_S02 的 adapter 能力声明生成 vendor × 信号族矩阵：presence/resources、sessions/roles、recent movement、tokens/cost、quota windows、workspace context、consented telemetry
- [x] 定义 cell 状态：observed / partial / unavailable / not_configured，并为每态保留证据来源；`observed` 是现有四槽已经提供的本地证据，`partial` 只用于复合信号缺一半，`unavailable` 表示没有本地证据，`not_configured` 表示需要用户同意的遥测尚未配置
- [x] 矩阵由 snapshot 与 `/api/capabilities` 提供，诊断面从同一 registry projection 渲染
- [x] **文档页从同一源生成，使 docs 与 code 无法漂移**；文档同时生成四槽表与七族覆盖表
- [x] 所有用户可见标签沿用现有 metric semantics/i18n 路由；三语 key 由 locale 校验器守住
- [x] 把矩阵确立为发布门：`TestCapabilityMatrixDocMatchesTheRegistry`、能力 API 测试、golden snapshot 和 UI build/locale gate 一起阻止伪支持或文档漂移

## 已落地部分（2026-09-20）

**触发事件不是排期，是一次真实漂移**：Antigravity 作为第二证据根接进 gemini adapter（`M02_S05.006.RSI`）后，`docs/coding-agent-evidence-adapters.md` 的手写能力表**完全没有反应**——全仓库没有任何东西比对过代码与文档。这正是本 sprint 存在的理由，所以先把这一格补上。

落地范围（2026-09-22，code → snapshot/API → UI → docs 同源）：

- `agent_registry.go`：`codingAgentAdapter` 增 `Evidence []string`（该 adapter 实际读取的磁盘形状，每个独立布局一条）与 `Note string`（为什么某槽缺席／某槽带什么陷阱）。十个 adapter 全部声明完毕。
- `capability_matrix.go`（新）：`capabilityMatrix()` 直接读注册表的四个能力槽——**nil 槽渲染为 `unsupported`，绝不软化、绝不从兄弟槽推断**；`renderCapabilityMatrixMarkdown` 产出带标记的生成区；`spliceCapabilityMatrix` 只替换标记之间的内容，标记缺失时报错而非猜测（防止手写散文被整体覆盖）。
- 文档表格改为 `<!-- BEGIN/END GENERATED CAPABILITY MATRIX -->` 包裹的生成区，`UPDATE_CAPABILITY_MATRIX=1 go test . -run TestCapabilityMatrixDocMatchesTheRegistry` 重新生成。
- 三个测试：doc 与注册表一致性门；nil 槽必须渲染 unsupported；**凡是解析 transcript 的 adapter 必须声明证据形状**，且 gemini 必须声明两个根（这条专门盯住「往既有 adapter 加第二个证据根」这个已经发生过的失败形状）。

本轮补齐了之前缺失的三端接线：`Snapshot.CapabilityMatrix` 与 `/api/capabilities` 复用 registry projection；诊断页展示 vendor × signal family 的四态覆盖；生成文档同时包含四个底层能力槽和七个信号族，避免 API/UI/docs 各自维护一张表。`capability_matrix.go` 的映射保持保守：process 只证明 presence/resources，discovery + transcript 才能支撑 sessions/roles 与 workspace_context，quota_windows 没有本地账本则明确 unavailable，consented_telemetry 在用户未配置时明确 not_configured。

**新表比旧手写表多出的真实信息**：`Evidence discovery` 列（旧表没有）、每个 adapter 实际读取的磁盘路径形状、以及 **antigravity 根**——旧表里它不存在。

**变异测试确认门有效**（两类都试过）：

| 注入 | 结果 |
|---|---|
| 删掉 gemini 的 antigravity 证据声明 | 两个测试同时变红（doc 陈旧 + gemini 应声明两个根） |
| 给 hermes 塞一个它并不具备的 Usage 槽 | doc 陈旧，实测打印出 `\| hermes \| … \| supported \|` 的错误行 |

**边界仍然明确**：七个信号族是四个 registry capability slot 的产品投影，不声称已经拥有 quota 或 consented telemetry 的运行时数据。`partial` 只由复合槽的一半存在时产生；单槽缺失不会被邻近信号补齐。若未来接入 quota ledger、官方 telemetry 或 sandbox 专用证据，只需扩充映射和对应 adapter 证据声明，并继续通过同一发布门。

## 验收标准（量化）

1. 修改一处 adapter 能力声明 → API、UI 面板、文档零手工编辑同步更新（测试证明）。
2. 100% 已渲染 snapshot 数据可追溯到矩阵 cell 与命名证据来源。
3. 审计测试：未观测 cell 渲染为标注空缺，绝非零值/估算/推断对等。
4. locale 校验器绿，全部新 key 三语齐备。
